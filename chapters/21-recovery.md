# 第 21 章 可靠性：副作用之后的未知窗口

## 最困难的故障发生在成功附近

设工具发送一次远程构建请求。服务已经启动构建，但网络在响应返回前断开。运行框架没有结果，不知道动作是否发生。直接重试可能启动第二次构建；直接报失败又可能误导用户。这个“外部成功、本地未知”的窗口，不会因为使用 JSONL、SQLite 或任务队列就自动消失。

文件编辑也有相同问题：文件替换已完成，结果日志尚未提交，进程被终止。重启后，聊天历史说“没有结果”，现实文件却已经改变。可靠系统必须允许“结果未知”状态存在。

## 至少区分六种执行状态

| 状态 | 已知事实 | 适合的恢复动作 |
|---|---|---|
| 尚未提交意图 | 未正式承担执行 | 可重新规划 |
| 意图已提交，尚未派发 | 框架准备执行 | 按策略派发 |
| 已派发，结果未知 | 外部动作可能发生 | 查询、核对或人工处理 |
| 已取得结果，尚未可靠提交 | 进程内曾知道结果 | 若结果已丢失仍需核对 |
| 结果已提交 | 可从记录恢复 | 复用结果，避免重复动作 |
| 验证已完成 | 实际检查给出结论 | 报告检查范围与证据 |

这张表是本书设计建议，并非四个项目都采用完全相同状态枚举。它帮助区分日志事实、外部事实和任务完成事实。

## 幂等必须绑定业务身份

为工具调用分配 UUID 只能关联日志，除非外部服务也把这个 UUID 当作幂等键，否则它不会阻止重复执行。真正的幂等需要服务记住相同业务请求，并返回原结果；或由工具通过可验证前置条件确保重跑不重复产生效果。

本地编辑可采用“预期旧内容哈希—目标新内容哈希”：旧内容匹配才修改，新内容已匹配则识别为可能已完成，其他情况停止核对。它适合特定文件替换，却不能泛化到发送通知、计费或任意 shell 命令。

## 重试应该属于哪一层

HTTP 客户端可能自带重试，模型 adapter 可能重试，主循环也可能重试。如果每层都各重试三次，一次逻辑请求可能产生远超预期的实际调用。DeepSeek Harness 的 pi-ai adapter 文档明确让框架持久步骤拥有可见重试，关闭 SDK 的隐藏重试，这是一种减少歧义的办法。〔D18〕

不同错误也不应统一重试。瞬时连接问题与参数无效不同，权限拒绝与资源不足不同，模型上下文超限与工具业务失败不同。重试策略应包含错误类别、上限、退避和总预算，并在可观察记录中关联到同一个逻辑请求。

## 取消不能回滚已经发生的世界

取消意味着不再启动新工作、尽量停止正在运行的工作、收集已发生结果并完成必要清理。它不意味着之前写入的文件消失，也不意味着已提交远程任务自动撤销。

DeepSeek Harness 会为未派发工具补合成结果，Pi 会按循环与信号处理终结，Codex 区分某些工具取消时是否仍需完成，Claude Code 区分用户中断与同伴错误。这些机制解决协议闭合或资源收敛，但不能独自提供业务回滚。〔D03〕〔P01〕〔C06〕〔A05〕

## 检查点与摘要各自负责什么

摘要让模型在有限窗口继续理解任务；检查点让执行器知道从哪里恢复；外部核验让系统确认副作用是否发生。三者缺一不可互相替代。自然语言“测试已通过”若没有对应结果记录，不应成为执行器跳过验证的唯一依据。

Pi Durable 的 replay 声明提供了明确示例：安全重放由工具显式承担，否则中断产生错误结果。Codex 的历史重建与 DeepSeek Harness 的迁移则提醒我们，检查点本身也必须满足兼容性与完整性要求。〔P12〕〔C09〕〔D11〕

## 故障实验应该怎样设计

在意图提交后、外部执行前、外部执行后、结果提交后分别注入故障。每次恢复检查两个东西：框架记录是否自洽，真实副作用是否重复。测试只比较最终回答文本无法发现重复提交。

读者实践时应先用可丢弃的目录与假服务，不要拿真实发布、计费或通知作为故障注入对象。这里的目的不是给所有操作增加审批，而是让恢复承诺有可重复验证的依据。
