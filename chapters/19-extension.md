# 第 19 章 扩展机制：依赖注入、生命周期与协议版本

## 扩展点按责任定义

常见扩展包括模型 provider、工具、上下文贡献、执行器、存储 provider 和 UI renderer。不要用一个任意修改全局对象的 callback 承载所有功能。每类扩展声明输入、输出、顺序、是否可短路、错误归属与资源释放方式。

```text
Extension {
  id, version, required_services[], provided_services[],
  register(context) -> Disposable,
  compatibility, trust_requirement
}
```

服务定义接口，provider 提供实现，consumer 使用接口。DeepSeek 的能力接口明确采用这三类角色；Pi 的扩展类型与 runner 则展示钩子式组织。〔D15〕〔P10〕〔P11〕

## 装载时先检查依赖图

构造有向图，检查缺失服务、重复 provider、循环依赖与版本不兼容。只有配置完整才激活消费者。不要发现 provider 缺失就静默跳过工具，否则用户看到的是能力随机消失。

加载失败需要回滚已注册贡献。注册返回 disposer，组合器按逆序撤销；已经启动的连接和 worker 也要等待清理。将“注册是一种资源”写进 API，能避免插件卸载后残留工具和监听器。

## Scope 是可见性范围

不同 agent 可以拥有不同工具与上下文贡献。scope 决定注册继承和事件接收，不能用字符串 prefix 代替真实身份。DeepSeek 使用不透明 scope key 与父子链，提供了避免范围混淆的参考。〔D09〕

scope 不阻止同进程恶意代码访问宿主模块。第三方不可信扩展应通过独立进程或受限协议运行，只得到明确定义的能力。安装一个具有宿主代码执行权的插件，本质上是重要信任动作。

## 热卸载要先停止新的借用

推荐状态 active → draining → disposed。draining 后不再把工具放入新 ToolPlan；已有步骤持有旧 runtime 引用，完成或取消后释放。引用数归零再关闭连接与卸载代码。超时无法清理时，报告 leaked/failed 状态，而不是假装释放成功。

同名新版本不能直接替换旧调用。旧调用恢复需要原版本或明确迁移策略；缺少原实现时返回阻塞，而不是用新参数解释猜测。

## 钩子组合需要定义短路规则

观察型钩子只读取事件，策略型钩子返回决定，中间件型钩子通过 next 继续。不同类型不要混成一个模糊返回值。瀑布中不调用 next 会短路，因此注册顺序属于行为语义。〔D16〕

mandatory guard 不接受普通插件放宽，后置脱敏不改变真实执行效果。插件异常由框架归一化，并说明是在准备、执行还是呈现阶段失败。一个日志插件报错不应无条件回滚已经完成的写操作。

## MCP 接入的实际工作

MCP 工具接入仍要管理 server 生命周期、连接 readiness、schema 变化、认证、超时和名称冲突。远端工具声明的只读或并发提示不能自动成为宿主强安全保证；部署方需要自己的信任与权限规则。

规范化远端名称后保留 server/tool 原始身份，授权与审计使用实际目标。server 重连后 schema revision 变化，下一请求更新工具计划；进行中的旧调用按原版本结算。

## Code mode 不应该绕过底层工具

让模型写一段程序批量调用工具，能减少请求往返，但带来脚本 CPU、内存、运行时间和嵌套调用管理。脚本只拿到受控工具代理，不拿宿主任意 API；每个嵌套调用走共同策略与记录路径。

如果脚本中断，已完成子调用结果应可发现；重跑脚本需要稳定 nested key 和子调用 replay policy。Pi Durable 的嵌套调用和 Pi 通用 runToolCall 分别提供持久与非持久层面的参考。〔P12〕〔P01〕

## 验收

缺少 provider 要在启动时失败；加载一半异常要撤销注册；卸载期间新请求看不到工具、旧调用仍正确结算；renderer 故障不丢执行结果；远程 server 改 schema 不用旧 grant；嵌套调用不能绕过权限。插件市场和动态安装应在这些机制稳定后再开放。
