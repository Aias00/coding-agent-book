# 第 12 章 Pi：工具钩子、并发模式与编辑前置条件

## 从校验到结果终结

Pi 的工具管线查找工具，准备参数，按 schema 验证，执行 `beforeToolCall`，运行工具，再执行结果后处理。未知工具、校验错误与被阻止的调用能够形成错误结果供模型观察，而不是让整个任务无条件崩溃。嵌套工具调用也可以走共享的 `runToolCall` 路径，让相同钩子继续生效。〔P01〕〔P02〕

这对 code mode 或工具桥接尤为重要。如果外层调用经过权限检查，内层工具却直接调用实现函数，那么桥接就可能绕过原有策略。共享执行管线把策略检查留在真正执行每个工具的位置。

## 并行模式的两个顺序

低层循环支持 sequential 与 parallel 两种批次模式。parallel 模式依次准备调用，获准执行的工具体并发运行；工具结束事件可以按照真实完成顺序发出，工具结果消息随后按助手源顺序形成。〔P01〕〔P02〕

因此你可能先看到第二个搜索工具完成，但最终模型历史仍把第一个调用结果排在前面。完成通知顺序服务实时性，消息顺序服务稳定上下文。把二者分开，才能准确解释界面与重放的差异。

与 DeepSeek Harness 的有界滚动池相比，Pi 这里的低层并行批次并不是同一类调度器。它不应该被直接描述为内建资源感知计划器。若应用需要针对服务限流或文件锁做更多控制，应在工具实现或更高层加入相应机制。

## 输出截断为什么会阻止工具执行

模型达到输出长度上限时，工具参数可能只生成了一部分。即便某个 JSON 修复器碰巧把残片解释为可校验结构，它也不一定是模型原本要表达的完整行动。该循环在 stop reason 为 `length` 时，对这条消息里的工具调用统一生成错误，不执行这些可能被截断的参数。〔P01〕

这是一个很好的防守例子：语法有效不等于行动完整。假设模型原本要表达三个互相配套的编辑，只生成第一项就被截断，执行第一项可能让文件暂时处于错误状态。保守拒绝让模型有机会重新发出完整调用。

## 精确编辑如何降低误改

Pi 编辑工具接收一个文件内的多处替换，每处 `oldText` 需要匹配原文件中的唯一、互不重叠区域。所有替换对同一份原始内容匹配，而不是前一条修改后的内容。工具还处理换行等文本细节，并产生可显示的 diff 与 patch。〔P07〕

修复案例里，如果用户在模型读取后已经修改了目标函数，旧文本不再匹配，工具应停止并要求重新读取。这个机制比按绝对行号写入更能表达前置条件，但不能防止所有并发修改，也不能代替多文件事务。

## 同文件串行不等于全局串行

`file-mutation-queue` 根据路径及可取得的 realpath 建立文件级队列。同一文件的变更依次执行，不同文件仍可并行；注册队列负责协调队列登记。〔P08〕

这种局部串行比把全部写操作用一个全局锁包住更有并发空间。不过它是进程内协调：外部编辑器、其他进程或文件系统路径变化不会自动服从这份队列。它也不能保证“修改 A、修改 B、运行测试”三步成为一个原子操作。

## 工具结果中的两种信息

模型需要的是可据以决定下一步的结果内容；界面还需要 diff、位置和结构化细节。后处理若改了文本内容，却没有同步更新关联结构化内容，可能使两种消费者看到互相矛盾的事实。Pi 类型说明明确了结果字段覆盖的语义，提醒扩展作者不能假设深度合并。〔P02〕

练习：一个后置钩子把错误结果改成成功文本，却保留 `isError: true`，会怎样？检查要点是不同消费者可能分别按文本和标志判断，产生冲突。工具结果应该作为一致的终结对象处理，而不是任意拼接几段字符串。
