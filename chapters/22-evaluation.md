# 第 22 章 评测与可观测性：衡量完成任务的代价

## 成功率必须有可执行定义

“智能体成功修复漏洞”至少需要满足：目标测试通过、相关回归没有失败、改动符合范围、未破坏用户已有工作。如果只检查最终回答含“已修复”，会把自我报告当作事实。若只检查测试通过，又可能奖励删除测试或绕过校验的方案。

修复案例的最低验收包括：前缀相似的兄弟路径被拒绝，正常子路径被接受，实现与测试都有合理变更，未修改任务之外文件。更严格的评测还需要隐藏测试和代码审查，但隐藏测试本身也可能有误，需要保留复核机制。

## 用相同任务比较不同运行框架

比较 harness 时，应尽可能控制模型、温度或采样配置、仓库初态、工具能力、执行权限和预算。模型接入协议不同、可用能力不同，结果就不再只反映运行框架。无法统一的变量应作为条件明确写出。

每个任务还应重复执行，报告分布而非仅报告最好一次。本书没有实施这样的跨产品真实模型评测，因此不会给出速度、准确率或成本胜负。

## 不要只看总耗时

可以把总时间拆成模型等待、模型生成、工具等待、工具执行、用户审批和恢复开销。流水重叠时这些部分不能简单相加，应根据时间线解释关键路径。一个工具运行二十秒，并不意味着优化它必定让总任务缩短二十秒，可能它原本就与模型生成重叠。

工具调用数也不是越少越好。少一次读取可能意味着更快，也可能意味着未经核对直接编辑。更有意义的指标是完成质量、无效重复、可恢复失败及单位成功任务成本。

## 最小可观测数据集

设计建议是为会话、用户回合、模型步、尝试和工具调用分别建立身份，记录它们的父子关系。工具记录至少说明名称、开始与结束、结果类别、权限来源、输出是否截断；模型记录至少说明实际路由、耗时、用量和失败类别。敏感参数可用受控引用或脱敏摘要替代。

这些字段与前文四套系统中的协议、事件、请求头和执行元数据相呼应，但具体字段名称并不通用。适配器应该保留原始语义，不要为了统一图表把“被用户取消”与“执行错误”合并。

## 事件记录的三种消费者

产品界面需要可理解进度，调试者需要解释执行因果，合规审计需要知道授权与副作用。三者可以共享关联身份，但不必拿到相同内容。把完整命令、私密代码和访问令牌都发往统一遥测平台，不是必要的可观测性。

Claude Code 将 progress 与主 transcript 分开，DeepSeek Harness 区分实时帧与持久结算，Pi 将 UI 自定义状态与模型消息区分，这些都说明“所有事件全量永久保存”不是唯一设计。〔A10〕〔D04〕〔P05〕

## 建立故障矩阵

| 故障位置 | 要验证的行为 | 不足以通过的表现 |
|---|---|---|
| 模型流中断 | 失败尝试可区分，未执行不完整调用 | 最终回答仍像成功 |
| 权限拒绝 | 工具未产生被禁止副作用 | 模型说自己遵守 |
| 工具超时 | 进程与结果状态明确 | 只显示 timeout 文本 |
| 写后崩溃 | 核验现实状态，不盲目重跑 | 聊天恢复正常 |
| 压缩后继续 | 用户约束和未完成事项保留 | 摘要读起来流畅 |
| 多 agent 冲突 | 改动有归属，可发现冲突 | 每个子任务都自报完成 |

## 从评测反推实现优先级

若大部分失败来自工具输出过长，先优化输出和检索；若来自重复恢复，先改善幂等与记录；若来自中途纠正失效，先处理队列边界。不要在没有失败分类时先增加 agent 数量或换一套提示词。

练习：两个系统分别成功 8 次和 9 次，每个只跑 10 个任务，能否得出稳定排名？检查要点是样本、任务分布、随机性和条件都不足，需要更多重复与误差解释。数字精确不等于结论可靠。
