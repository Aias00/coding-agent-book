# 序言：设计一套能够交付代码的 Agent

本书回答一个具体问题：如果从零实现 AI Coding Agent，应该怎样划分模块、定义数据结构、连接模型和工具，并让系统在真实开发环境里正确处理修改、测试、中断与恢复？

我们以一个贯穿任务推进设计：用户要求修复工作区里的路径判断函数，补充测试，并给出验证结果。Agent 要搜索代码、读取目标文件、形成修改、运行定向测试、根据失败继续，最终交付差异与证据。我们逐步把这个流程变成接口、状态机、存储结构与可运行程序。四个现有项目提供设计依据：Codex 的步骤上下文和工具编排，DeepSeek Harness 的服务组合与日志投影，Pi 的循环接口和会话结构，以及 Claude Code 发布包中可见的工具、权限和上下文机制。

第二版将“设计与实现”设为全书主线。章节按系统问题组织：怎样建立执行内核，怎样保证工具声明与实际实现一致，怎样接受流式参数，怎样控制文件修改，怎样绑定授权，怎样恢复结果未知的调用。项目源码出现在相关设计旁，用于证明已有实践或解释替代方案。读者不必按四个项目分别学习同一组概念。

2.1.0 增订进一步补齐任务业务流程、工具注册与暴露、Skill 渐进加载、MCP 桥接，以及四份源码各自的上下文压缩路径和设计取舍。新增专题采用“源码事实—分析判断—设计建议”的叙述顺序，先给实际函数与数据关系，再解释收益和代价。

## 你将得到哪些实现材料

每个核心章节给出五类内容：需要解决的具体问题；接口、字段及其所有者；正常流程和失败流程；并发或持久性约束；可执行的验证方法。关键算法用伪代码解释。代码块中标为“设计接口”或“伪代码”的部分是建议方案，不应直接当作完整库使用。

仓库中的 `reference_agent/` 是独立编写的可运行参考内核，演示模型响应驱动循环、工具注册与校验、权限绑定、SQLite 事件提交、并发读取、文件前置条件和保守恢复。它使用可替换的模型接口，默认脚本模型用于无密钥复现；不声称具备真实模型的代码推理能力。`labs/` 保留较小的故障窗口实验，方便单独理解写入后崩溃。

书中的完整方案比参考程序覆盖面更广。例如操作系统沙箱、长期后台进程、远程 worker 与多租户身份都给出接口、时序及验收要求，但没有为了展示“功能齐全”而提供未经验证的生产实现。每处都区分建议、已有源码事实和本仓库确实实现的功能。

## 阅读时应带着的三个问题

第一，谁拥有状态？模型流、工具、UI 和存储不能同时修改同一份会话对象。第二，行动发生到哪一步？准备、批准、派发、执行完成与结果提交是不同阶段。第三，下一次模型请求依据哪些事实？屏幕上显示过的字符、已经提交的消息和当前文件内容，不能不加区分地混在一起。

例如一个编辑已经写入，成功结果尚未保存，进程突然退出。系统恢复后缺少结果，却不能因此认定编辑没有发生。这个细节会贯穿工具设计、持久化和恢复章节。一本实现方案必须能解释这种情形，而不能只画出“模型—工具—模型”的正常流程。

## 源码证据与适用范围

研究快照固定在 2026-10-30。三个开源仓库使用完整 Git 提交号；Claude Code 使用本地 2.1.88 发布包，其被引用的 14 个提取实现文件已与 source map 嵌入文本对照。完整出处、85 个证据文件的哈希和定位见附录 B。编号如〔C01〕、〔D03〕用于连接方案与具体参考，不表示所有建议都已经由这些项目实现。

源码事实给出项目、快照、函数及证据编号；分析判断说明依据和适用条件；设计建议明确属于本书归纳。源码只能确认客户端行为时，不补写服务端内部机制。固定格式提示与机械边界检查，也不被当作已经证明语义保真的证据。后续修订继续按这一口径处理。

本书没有公布四个产品的统一性能排名。默认值如并发数、输出限额和请求预算，是本书参考设计的起点，部署前需要通过任务集和故障测试校准。不存在一个适合所有模型、仓库和执行环境的固定参数组合。

## 建议的阅读顺序

准备开发第一版的读者，先读第 1—8 章，建立完整主循环与工具管线，再完成第 23 章。已有产品的工程师可以优先读文件修改、授权、上下文压缩和恢复章节，检查自己系统是否表达了相应前置条件与失败终态。平台工程师可重点看执行隔离、单写者、扩展生命周期及多 agent 的资源归属。

读完以后，判断自己是否理解某个模块的方法很简单：给它注入一次参数截断、一次权限过期、一次并发编辑、一次写后崩溃，说明应留下什么记录、界面显示什么、系统下一步做什么。能回答这些问题，方案才开始接近可实现。
