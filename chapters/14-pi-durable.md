# 第 14 章 Pi Durable：把继续执行写成状态机

## 为什么持久任务需要另一套机制

实验性的 `pi-durable` 将对话、生成和工具执行组织为可持久任务。任务在阶段边界保存检查点，恢复后从检查点继续；模型生成任务拥有工具子任务，并等待它们的结果。提交后再暴露状态的目标，使界面观察与存储事实有更强的对应。〔P12〕〔P14〕

它的 README 明确标为实验性，API 可变化。本书使用它说明设计机制，不建议把本地目录中的用法当作长期稳定公共接口。

## 检查点必须包含下一阶段所需信息

一个任务阶段读取文件、决定编辑，然后返回带检查点的新状态。进程退出后，阶段可能从顶部重新运行。因此阶段中读取的局部变量若没有进入检查点，就不能指望恢复后还存在；外部副作用若没有幂等安排，也不能指望重跑自动安全。〔P12〕

持久等待同样不是把线程睡在内存里。任务可以结束当前阶段，保存唤醒时间与检查点，之后由调度器唤醒。这样计时器能跨进程重启，也不会长期占用一次函数调用栈。

## 工具的 replay 策略是核心承诺

文档明确说明：工具意图在执行前提交；中途崩溃后，只有声明 `replay: "safe"` 的调用才会重跑，否则形成 interrupted 错误结果，并保留已经提交的输出。〔P12〕

这是对不确定副作用的诚实处理。读取文件一般容易安全重试，发送邮件则不能仅因框架没拿到结果就再发一次。声明安全重放是工具作者承担的责任，不是框架自动证明。即便标为安全，外部效果仍需要业务幂等支持。

## 嵌套调用怎样避免重复启动

嵌套工具调用拥有自己的持久身份，可以用位置或显式 key 关联。可安全重跑的父调用恢复后，以同样顺序或 key 再次访问嵌套调用时，可以取得已有结果或进行中的任务，而不是无条件新建。被中断的子调用仍遵守自己的 replay 策略。〔P12〕

修复案例里，父工具可以先读取文件，再调用测试工具。如果父阶段重跑，稳定 key 有助于复用已经完成的子结果。但如果现实文件已经变化，旧测试结果是否仍有效是另一个问题，调用身份还需要与输入版本或前置条件配合。

## Inbox 与工作边界

durable 的 inbox 保存可提交的输入，阶段边界选择并应用输入。队列不只是传送文本，还与 reset、steering 和后续输入的归属相关。其状态必须进入持久文档，才能在重启后保留相同意图。〔P13〕

这与普通 agent-core 的内存队列具有相似产品目标，但持久性层次不同。分析或集成时要明确自己使用的是哪一层，不能因为 API 名称相近就混用恢复保证。

## 崩溃循环也需要熔断

某项工作若每次恢复都在下一个检查点前耗尽内存，自动恢复会变成无限崩溃。文档说明调度器记录被打断的运行，达到重启限制后将任务停放，并提供检查和重试入口。〔P12〕

这揭示了自动化可靠性的另一面：恢复次数越多并不总是越可靠。系统需要让不可自行修复的任务变得可见，由用户修正输入、资源或实现后再继续。

## 可以借鉴但不能过度推导

这一设计将检查点、任务归属、持久等待和重放政策作为明确概念，适合长期任务。但它仍不能把本地存储与任意外部系统合成一个事务。所谓 durable，应理解为框架状态可恢复，并对中断作出有定义的决策；不能理解为所有副作用恰好一次，或任何中断都可无感继续。
