# 第 13 章 Pi：会话树、压缩与项目可信度

## 会话为什么是一棵树

coding-agent 的会话记录带 `id`、`parentId` 和时间戳。当前有效历史从选定叶子沿父关系向前追踪，而不是把文件中所有记录按时间排序就发送模型。记录包含消息、模型变化、压缩、分支摘要和扩展数据等不同类型。〔P05〕

用户尝试一条修复路线后发现不合适，可以回到旧节点继续探索。旧分支仍留在记录中，但不应污染当前模型上下文。树形结构让保留探索过程与选择当前工作路线可以同时成立。

## 自定义状态与模型内容要分开

会话接口区分用于扩展持久状态的 custom entry 与会进入模型上下文的 custom message。工具 UI 的折叠状态、扩展索引等数据不一定应该成为模型输入；面向模型的补充信息则应该走可解释的消息投影。〔P05〕

若把所有扩展数据都转成用户消息，既浪费窗口，也可能把未经审查的内部状态当作指令。如果全部只保存在私有状态里，恢复后模型又可能丢失必要约束。选对记录类型，比事后“加一个过滤器”更可靠。

## 压缩要携带系统与工具状态

压缩记录除摘要外，还包括保留起点、压缩前 token 数、可选扩展细节以及完整的系统消息状态。压缩实现追踪读取与修改过的文件，并使用会话投影选择内容。系统消息被当作提示状态处理，而非普通待总结的对话文本。〔P05〕〔P06〕

路径修复的摘要应保留“先别修改实现”的最新约束，以及修改和测试的实际状态。若只总结助手已经做了什么，却没有保留用户限制，下一轮可能在看似连续的会话中越过原有范围。

本快照有默认压缩参数，但设计理解不应绑定某个数字。真正要观察的是预留输出空间、保留近期尾部、压缩触发点和压缩失败的处理。窗口越大也不能免除这些问题，只会推迟它们出现。

## 项目资源为什么需要信任判断

项目目录中的配置与扩展可能执行代码、加载资源或安装依赖。`resolveProjectTrusted` 处理显式覆盖、扩展决策、存储决策、默认策略和交互选择。在没有 UI 且没有足够授权的情形下，它有保守返回路径。〔P09〕

这不是每次工具调用的审批。项目可信度决定是否加载项目资源，工具授权决定某项行动能否执行，沙箱决定执行后触及哪些资源。三者解决的问题不同。信任一个仓库加载扩展，可能意味着允许扩展在宿主进程中运行，应以实际资源加载语义评估风险。

## 扩展体系的优势与约束

扩展可以接入请求、会话、工具、UI 和生命周期，runner 负责运行与协调这些贡献。丰富的钩子使产品可定制，也要求作者遵守返回值、失败和字段替换约定。〔P10〕〔P11〕

同一个扩展若在交互、打印和 RPC 模式下运行，不能假设始终存在可交互 UI。读取源码时，需要把扩展类型与 runner 的实际调用位置一起看。接口中有一个事件，并不证明每个入口都会以同样方式使用它。

## 恢复聊天与恢复任务的分界

普通 coding-agent 的会话树和压缩解决有效历史重建；它们本身不等于完整的持久任务调度器。若进程在外部写入后退出，恢复聊天能告诉模型过去已记录的内容，却未必能判定失落调用的真实结果。接下来 durable 包提供的是另一个层次的机制，不能把其保证直接扩展到所有 Pi 使用方式。

练习：分支回退以后，磁盘上的代码会自动回到旧状态吗？检查要点是会话分支选择与文件版本控制不同，除非另有机制显式操作工作区。改变模型记忆不等于回滚现实文件。
