# 第 18 章 Claude Code：上下文预算、记录链与后台任务

## 大输出首先是预算问题

可见查询路径在模型请求前处理工具结果预算、微压缩和自动压缩。Tool 类型还允许设定结果大小限制，把过大结果持久到文件，并向模型返回预览与引用。某些自带限制的工具会采用不同策略，避免“读取结果再次溢出并保存”的循环。〔A03〕〔A04〕〔A08〕

这些机制说明，压缩不只有一次大摘要。运行框架还可以在更细粒度上限制重复结果与长输出。实现时要保护证据：用量降低若以删除关键错误信息为代价，可能让模型重复工作，最终反而更慢。

## 自动压缩需要保留安全余量

自动压缩实现从上下文窗口中扣除输出预留，再确定触发阈值；它还维护连续失败计数和恢复状态。源码给出了具体常量，但它们是该版本实现细节，不是所有模型与服务都适用的经验公式。〔A07〕

将窗口用到最后一个 token 才压缩往往太迟，因为生成摘要本身也需要输入与输出空间。更稳妥的设计是预留压缩与故障恢复余量，并阻止压缩失败无限重试。内部注释中的统计背景可以解释设计动机，却不应该作为本书独立验证的产品遥测事实。

## 压缩之后仍要知道真实完成状态

修复任务中，摘要可以缩短搜索细节，但不能丢掉用户约束、已写入文件、测试未完成和当前待决策事项。工具结果引用也必须保持有效，否则摘要说“完整日志见某文件”，恢复后那个文件却已被删除，会留下不可验证的结论。

因此压缩质量应通过后续任务是否正确继续来评估，不能只看摘要是否流畅。一个很短却丢失限制的摘要，可能比长一点的结构化摘要更昂贵。

## Progress 为什么不能进入主记录链

会话存储区分 transcript message 与短暂 progress。有效记录通过 parent UUID 关系形成链，旧进度记录的历史兼容需要专门桥接。可见代码明确避免把当前 progress 当作正常会话消息参与主链。〔A10〕

这个细节很有启发：UI 中的一条节点不一定是一条对话事实。把实时进度节点无差别塞进父链，会增加恢复时的歧义，使真正消息与仅供展示的状态混在一起。持久记录应围绕语义设计，再让 UI 从语义渲染，而非反过来序列化整个界面树。

## 恢复需要重建选中的有效链

存储和恢复模块根据会话记录重建上下文，处理消息身份、链关系及相关元数据。恢复的意义不是把所有磁盘行拼成字符串，而是选出有效历史，再恢复运行所需状态。〔A10〕〔A16〕

它仍然不自动证明丢失连接期间某项外部动作没有执行。和前三个系统一样，会话恢复与副作用恢复必须分别评估。

## 后台 agent 增加了归属问题

AgentTool 可见实现涉及后台任务、恢复参数与工作目录隔离等机制，也有构建与特性条件。工作树可以把文件修改分开，但不会自动隔离网络、环境变量、凭据和共享端口。〔A13〕

后台任务还需要回答：父会话关闭后谁管理它，完成通知如何关联，用户能否中断，结果在哪个目录产生，以及修改如何合回。工具返回一个任务编号只是开始，后续生命周期才决定功能是否可靠。

## 从这一篇带走什么

Claude Code 可见实现把工具执行、权限、人机交互、上下文节制和后台任务紧密组织在一起。它提供了观察成熟产品复杂度的材料，同时也提醒研究者约束结论：本地版本、提取可信度、特性门控和外部服务可见范围，都需要写进分析方法。

对自建产品最有价值的借鉴，是让每一项 UI 状态对应明确执行事实，让每一种执行事实都有可以恢复和解释的位置。
