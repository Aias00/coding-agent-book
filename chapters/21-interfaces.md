# 第 21 章 产品接口：CLI、IDE、Web 与人机协作

## 一个控制协议承载多个界面

建议命令包括 create_session、submit_input、start_turn、cancel_turn、resolve_approval、read_artifact 和 subscribe。命令携带 client_request_id，用于网络重试去重。返回 accepted 不等于 completed，长任务通过事件继续报告。

事件至少包括 input_accepted、step_started、assistant_delta、tool_started、tool_settled、approval_requested、turn_ended。名称可变，语义要稳定。Codex app-server 展示了把核心执行能力通过结构化客户端协议暴露的思路。〔C15〕

## UI 状态来自执行事实

等待模型、工具排队、等待授权、命令运行、取消收敛和结果未知应该显示不同状态。“Running” 不能覆盖全部等待；否则用户看到长时间不动，不知道该批准、等网络还是检查环境。

搜索读取可合并展示，编辑突出 diff，验证显示命令、退出码与范围。工具结果将模型内容、结构化事实和呈现 metadata 分开，renderer 失败仍能显示基本状态。Claude Code 的 Tool 产品字段为此提供参考。〔A04〕

## 授权提示要让人判断真实范围

显示动作、目标、工作目录、权限新增、预期效果及可选决定。不要让用户阅读内部类名或无关 JSON。也不要把“运行测试”作为全部解释，如果实际命令会联网安装依赖，应展示这部分范围。

一键允许当前动作与保存长期规则是不同操作，UI 应明确区分。审批页使用稳定 decision_id，刷新和重复点击不能批准新对象。拒绝可以附理由，作为下一步可解释输入，但理由不应被自动转成宽泛授权。

## IDE 集成最重要的是版本

IDE buffer 可能尚未落盘，工具读取磁盘却看不到用户屏幕上的新内容。需要明确以 buffer 还是磁盘为事实源，编辑请求绑定文档版本；应用 patch 时通过 IDE 的版本检查机制，不能假设磁盘 hash 代表编辑器状态。

跳转位置同时携带路径、行列与版本；版本失效时定位只作为近似导航。诊断和测试结果也标记对应代码版本，避免在旧错误上继续修改。

## CLI 的退出与管道语义

交互模式可以展示进度，机器模式应输出 JSONL 或独立协议流。stdout 保留结构化结果，诊断去 stderr，避免彩色日志破坏消费者解析。退出码区分成功、部分、取消和失败，具体约定写进文档。

非交互环境遇到 ask 应暂停或失败并给出需要的权限，不能等待永远无人回答的终端提示。明确授权参数需要经过与 UI 相同策略路径，而不是隐藏后门。

## 重连、快照和幂等提交

浏览器重新发送 submit_input 时，服务按 client_request_id 返回同一 input identity。订阅从 last_seq 继续，过期则提供 snapshot。提交命令与订阅事件是两条通道，但通过身份关联，不能只靠“最新一条”配对。

临时模型增量可以丢失后从结算消息重建；审批请求和工具终态必须可恢复。慢客户端不能阻塞整个执行内核。

## 用户中途接管代码

当用户开始编辑同一文件，系统应标记工具读取版本可能失效。Agent 修改前检测冲突，向模型或 UI 说明重新读取。不要通过锁住整个编辑器来解决所有冲突，也不要假设用户停止输入后工作区就回到旧版本。

最终报告列出变更、验证、未完成项和受影响范围。没有验证就说明未验证，不能用“应该可以”替代已执行结果。可读性与事实准确性都属于产品质量。

## 验收

相同动作在 CLI 与 Web 得到相同权限结果；刷新审批不重复执行；断线后恢复正确终态；IDE 未保存修改不会被覆盖；无 UI 环境不死等；慢订阅者不会拖慢其他会话。参考书在线阅读器与 Agent 产品协议是两个不同系统，不能用阅读器测试代替这些验收。
