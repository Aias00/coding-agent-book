# 第 14 章 代码理解：搜索、符号、LSP 与证据失效

## 先用最便宜的线索缩小范围

代码检索通常从文件名、错误栈、符号名和文本搜索开始。直接把全仓库向量化并不能替代这些精确线索。推荐检索顺序：路径与配置 → 精确符号或文本 → 相关调用者与测试 → 必要时语义召回 → 限量读取原文确认。

每次检索输出位置与证据身份，不直接让摘要代替源文件。模型据此选择下一批读取，避免将大量不相关内容一次塞满上下文。

## 定义统一证据对象

```text
CodeEvidence {
  workspace_id, path, blob_hash,
  start_line, end_line, symbol?, source_kind,
  content_ref, retrieved_at, index_revision
}
```

路径和行号帮助导航，blob_hash 说明内容版本，index_revision 说明检索索引版本。索引旧并不一定要全量重建，但必须承认结果可能过期，并在修改前重新读取真实文件。

## 文本搜索的工程细节

默认遵循 ignore 规则并限制超大、二进制和依赖目录；用户明确指定的文件可进入另一路径，但仍经过权限检查。工具返回命中数量、是否截断、搜索范围和模式解释方式。正则与字面量是不同模式，不要让模型误把特殊字符当普通字符。

限制输出之外还要限制搜索时间与扫描范围。一个灾难性正则或远程全盘扫描会消耗执行资源，不能仅通过截断展示解决。外部搜索程序的退出码需区分“无匹配”和“执行错误”。

## LSP 给语义位置，也带来版本约束

LSP 可提供定义、引用、诊断与重命名，但服务可能尚未初始化，文档版本可能落后，诊断可能异步到达。每条结果需要说明来自哪个 server、哪个 workspace 和哪个文档版本。先等 readiness，再请求；超时有退回文本搜索的明确路径。

批量重命名返回 workspace edit 时，检查所有目标文件的版本与权限，再执行。不能因为结果由语言服务器生成就跳过修改授权。server 也是执行环境的一部分，启动参数和插件加载需要管理。

## 多跳检索要有停止规则

模型从函数跳到调用者，再到配置，再到测试，容易无限探索。可以给每个问题设置 evidence budget：读取文件数、累计 token、检索轮数和当前假设。若已有足够证据支持一个可验证修改，就转到实现；若线索冲突，记录具体待解问题再继续。

检索器可输出“建议相关文件”，但不能把建议升级成事实。例如同名函数不一定是实际执行路径，测试目录出现关键字不一定覆盖目标平台。最终需要沿调用与入口确认。

## 缓存与索引失效

文件修改后更新对应哈希，失效相关 chunk、符号位置和诊断。整个仓库发生分支切换时，不要继续使用前一棵工作树的向量索引。缓存键至少包含 workspace identity、文件内容版本和工具语义版本。

未提交用户改动应纳入当前检索。只索引 Git HEAD 而忽略工作区，会让模型根据旧文件生成补丁。可采用 HEAD 索引加工作区 overlay，查询时优先覆盖改动文件。

## 参考与验收

四个项目中的文件、工具和执行环境机制说明了统一能力与位置引用的重要性；本章给出的是面向自建系统的组合方案，并不声称它们采用同一检索架构。能力替换时尤其要保持 LSP、文件和测试处于同一执行世界。〔D15〕〔C07〕〔P07〕

验收用包含同名函数、过期索引、未提交改动和生成代码的仓库。让检索结果指出真实执行入口；编辑后再次查询应反映新内容；超时或无命中应返回明确结果，不能编造一个似乎合理的文件位置。
