# 第 17 章 Claude Code：权限决策与 shell 的特殊复杂性

## Allow、deny 与 ask 是三种状态

权限系统需要表达允许、拒绝和需要进一步决策。`CanUseToolFn` 接收工具、输入、执行上下文和调用身份；交互 hook 再把相应决策映射到 UI 或继续执行。执行管线最终只有在允许时进入工具调用，拒绝会形成可观察结果。〔A06〕〔A14〕

ask 不是一个布尔假值。它代表工作暂停等待一个决策者，这个决策者可能是用户，也可能是宿主集成。若异步等待丢失、重复提交或错误绑定到另一项调用，审批本身就会产生竞态。

## 规则匹配不是 shell 语义证明

包中有独立的权限规则、文件路径与 Bash 权限逻辑。因为 shell 命令包含管道、重定向、子命令、变量扩展与解释器，简单前缀判断很难准确表达实际效果。〔A11〕〔A12〕

比如允许 `python` 并不意味着只允许无害计算，允许 `git` 也不代表不会修改配置或调用外部程序。因此工具名规则更适合表达粗粒度用户偏好，真正的资源限制仍需要环境级控制和具体解析。本文的这一段是工程推理，不是对该产品某条规则可绕过的漏洞报告。

## 权限模式与环境能力要分开

一个产品可以提供不同交互模式，减少逐次询问或只允许计划。模式决定框架怎样作出授权选择，沙箱决定执行器实际能访问什么。前者如果放宽，不应该让文档误写成后者仍提供相同限制；后者如果受限，也不能让 UI 把所有允许动作都当成无需审查。〔A04〕〔A11〕

路径修复的最小授权通常是读取工作区、编辑指定文件和运行定向测试。若测试脚本可以联网或读取家目录，实际权限范围远超过“跑测试”三个字。权限提示应帮助用户理解有效范围，同时避免展示与判断无关的实现细节。

## 计划模式需要机器规则支撑

告诉模型“先写计划”有助于引导行为，却不是禁止执行。若工具列表仍包含高权限操作、执行器也不检查状态，模型偶然越过计划约束仍会产生副作用。可靠的计划阶段需要能力暴露或授权规则配合。

四个项目都提供可以承载策略的位置，但不能仅凭有一个 Plan 工具就推导出严格只读。本书在横向比较中把“有交互能力”与“有强制执行边界”分别列出，以避免这种概念混淆。

## 自动决策仍需要完整记录

可见执行路径记录权限决策来源与相关指标，用来解释允许或拒绝来自配置、hook 还是用户选择。记录来源有利于排查“为什么这次没问”的问题，但日志需要保护命令参数、路径和凭据。〔A06〕

在企业系统中，审批事件最好包含经过规范化的行动摘要、权限范围、有效期、决策来源和调用关联。不要把完整私密输入无条件复制到遥测系统，也不要只记一个 allow 而丢失其前提。

## 审计顺序应该如何安排

先检查外部输入在哪里进入，再检查工具 schema 与语义校验，随后检查规则组合与参数改写，最后检查操作系统、网络和凭据边界。单测能够覆盖局部分支，但 shell 与路径策略还需要针对真实平台执行验证。

练习：用户允许一次删除临时目录，系统能否以后不再询问所有删除？检查要点是允许范围需要绑定路径、动作与有效期；一次行动同意不能自动泛化成无限能力。这一结论来自授权语义，与采用哪一家模型无关。
