# 第 4 章 Codex：工具计划、执行门禁与并发

## 工具声明与执行实现必须对应

模型看到的是名称、说明和参数 schema，实际执行依赖的是运行时实现。Codex 的 `ToolRouter` 同时保存注册表、模型可见 specs、工具模式与 code mode 名称映射；`spec_plan` 则负责形成最终工具计划。工具能否出现在请求中，与它如何被路由执行，在这里有明确的连接。〔C03〕〔C04〕〔C11〕

这解决了原型系统常见的问题：请求里宣告了一个工具，但执行器没有加载；工具被禁用后，模型仍从旧声明中选择它；两个扩展注册相同名称，最后加载者静默覆盖前者。具体冲突处理仍需查看注册与计划构建规则，但把声明与实现统一规划，本身就让这些错误有了集中检查位置。

工具可见性还有直接暴露、延迟发现和 code mode 等差异。工具数量增多时，全部 schema 放进每次请求会增加上下文与选择负担。延迟暴露能缓解这一点，却要求系统维护“存在”“已经声明”“当前可执行”之间的一致性，不能只从提示词里删掉一段说明。

## 一次调用经过哪些门

可以把主要职责概括为下面这条教学路径，具体工具可能有自己的附加步骤：

```text
模型工具项 → 名称与载荷解析 → 注册运行时
           → 并发准入 → 审批/沙箱编排 → 实际执行
           → 结果、元数据与生命周期事件
```

`ToolRuntime` 抽象工具如何在一次执行尝试中运行；`ToolOrchestrator` 负责审批、沙箱选择及沙箱拒绝后的重试协调。这里不是每个工具自己随意实现一套“有风险就问用户”的逻辑。集中编排能够使审批与执行环境的关系保持一致。〔C05〕〔C12〕

## 审批通过的究竟是什么

审批应该绑定到具体行动与权限范围。一次受限环境里的允许，不能自动变成脱离限制后的允许。该快照的编排代码明确区分执行尝试及沙箱覆盖情形，并说明升级沙箱后的尝试需要重新审查相应权限。网络审批也参与执行上下文，相关结果需要完成收尾。〔C05〕

修复案例里，“在工作区运行测试”与“允许测试联网下载未知脚本”是不同授权。即使它们在终端里表现为同一条命令的两次运行，权限范围已经变化。审批缓存若只用命令文本作为键，就可能忽略环境、目录与权限差异。

这是工程解释，不代表正文已经穷举所有审批缓存字段。要审计某个具体工具，应继续追踪它构造审批请求的代码及测试，不能仅凭编排器的存在宣布安全。

## 读写锁怎样表达工具互斥

工具运行时保留一个共享 `RwLock`。支持并行的调用取得读锁，不支持并行的调用取得写锁。因此多个并行调用可以同时进入执行阶段，独占调用则需要单独运行。运行时还区分准备等待、执行开始和取消处理。〔C06〕

这个锁的“读”和“写”是调度含义，不应直接等同于工具是否读写文件。一个只读取数据的工具可能修改共享登录状态；两个写工具也可能操作完全独立的资源。是否允许并发需要工具语义与共享状态共同决定，而非仅看函数名称。

对修复链来说，读取两个独立文件通常适合并行，修改实现后运行测试则存在明确依赖。并发机制只能允许动作重叠，不能自动替模型建立正确的依赖图。模型如果错误地在修改完成前测试，执行器不会凭一个锁就理解任务意图。

## 取消语义是工具协议的一部分

代码中的工具运行时允许表达某些调用在取消到来后仍需完成。准备阶段、等待执行锁和已经进入副作用阶段不能使用完全相同的丢弃策略。一个查询可以尽快结束；一个正在提交本地文件替换的操作，可能需要先完成到可解释的状态，再报告取消。〔C06〕

自建系统可以借鉴这一划分：工具应声明取消支持、可重试性与结果未知时的恢复方式。不要因为语言运行时允许取消 future，就把取消当作副作用消失。接口中没有表达出来的语义，最后都会以特殊分支进入主循环。
