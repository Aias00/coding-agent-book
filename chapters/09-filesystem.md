# 第 9 章 文件系统工具：路径约束与乐观并发修改

## 读取工具必须返回可用于修改的版本

建议读取结果包含 `path`、内容或选定行段、内容哈希、编码、是否截断、可继续读取的范围和工作区身份。只返回正文，下一次编辑就无法说明“基于哪一版文件”。行号用于展示，内容版本用于前置条件，两者不能互相替代。

对大文件按字节和行数同时限量；UTF-8 在切片边界要正确解码。二进制先识别，再返回元数据或受控产物，不把任意字节强行当作文本。读取 secret、忽略目录和控制面存储也需独立策略，不能认为工作区内全部文件都适合发送给模型。

## 路径规范化只能解决一部分问题

输入应明确是工作区相对路径还是已批准绝对路径。拒绝词法逃逸后，还要处理符号链接、真实父目录、大小写与路径别名。检查完成后，攻击者仍可能替换目录项，这叫检查与使用之间的竞态。应用级 `resolve()` 不能提供完整隔离。

可信单进程工具可采用拒绝符号链接并检查父链的保守方案；不可信仓库或多租户系统应让执行世界提供真实文件访问限制。Linux 等平台可考虑目录句柄和受限路径打开 API，具体实现按平台验证；不要把字符串前缀比较当作安全根。

## 精确编辑的前置条件

```text
EditRequest {
  path, expected_content_hash,
  replacements[{old_text, new_text}], encoding
}
```

取得同文件锁后重新读取。先比较哈希，再检查每个 old_text 在原文件里唯一存在，替换区域互不重叠；按位置从后向前生成新内容，或一次性重建。每项都针对同一份原文，不能让第二个 old_text 匹配第一项修改后的新内容。Pi 的编辑工具与文件变更队列可参考。〔P07〕〔P08〕

若哈希变化，返回 PRECONDITION_CHANGED，附当前版本信息并要求重新读取。不要自动模糊匹配并应用一个“差不多”的 patch。模糊匹配可以作为人工辅助模式，但不应默认获得与精确条件相同的安全承诺。

## 源码细节：Pi 的唯一匹配、模糊回退与进程内队列

前面的 expected_content_hash 接口属于本书建议。Pi 当前 edit schema 实际提供 path 与 edits，每项包含 oldText/newText；它没有要求调用者携带整文件旧哈希。prepareEditArguments 还兼容字符串化数组、单个对象和旧字段形式，转换后再进入验证与执行。〔P07〕

执行时先进入 withFileMutationQueue，再访问并读取文件，移除 BOM、归一化换行，计算全部替换，最后恢复 BOM 和原先检测的换行形式并写入。applyEditsToNormalizedContent 针对同一份原文寻找每项位置，拒绝空 oldText、多处命中、重叠和无变化，按反向位置应用以保持偏移稳定。〔P07〕〔P21〕

一个容易被说明文字掩盖的实际差异是模糊回退：fuzzyFindText 先找精确匹配，失败后对 NFKC、行末空白、引号、破折号及特殊空格作归一化。任何一项需要 fuzzy 时，匹配在统一归一化空间完成，再按受影响行把修改覆盖回原内容，避免把无关行一并规范化。它不是任意语义相似替换，但也不是严格逐字节匹配。〔P21〕

例如模型给出的 ASCII 引号与文件中的弯引号不同，这条回退可能仍找到位置。设计判断：它提高模型编辑容错，但受影响行可能承受规范化，且唯一片段匹配不等于整个文件版本未变化。需要严格补丁来源的宿主，应额外要求版本前置条件或提供可关闭的回退策略，不能只读 description 中的 exact 就承诺严格编辑。

队列使用 realpath 归并现存路径别名，路径尚不存在时使用 resolve 后的键；全局 registrationQueue 只串行登记，不同文件的正文仍能并行。队列是模块内 Map，不能阻止外部编辑器、另一进程或远端写者；默认本地 writeFile 直接调用 fs.writeFile，也没有在这条路径实现临时文件加 rename 的原子替换。〔P08〕〔P07〕

取消也有细节：代码在每次 await 后检查 signal，刻意不在 abort 监听器里立即释放队列，避免文件系统调用未完成就让下一编辑进入。写入后观察到取消仍可能返回错误，而文件已经改变，这正是第 17 章要单独处理真实效果的原因。〔P07〕

## 为什么检查哈希还要加锁

两个进程都读到 H0，都通过比较，然后分别写 H1 和 H2，仍然会覆盖。进程内锁防止同一执行器里的并发工具冲突；跨进程需要共享锁、文件系统原子能力或版本化工作区。哈希校验是乐观并发前置条件，本身不是操作系统级 compare-and-swap。

如果不能控制外部编辑器，至少在临近替换时再读并比较，并将仍然存在的竞态明确列出。不要声称两次哈希检查已经实现不可绕过的事务。

## 临时文件与原子替换

推荐在同目录创建临时文件，写完整内容，flush/fsync，保留必要权限，再原子替换目标。需要断电持久性时还应处理目录项同步。临时文件同目录有助于避免跨文件系统 rename 失败。

原子替换保证观察者通常看到旧文件或新文件，而不是半截文件；它不保证多文件一起替换，也不自动保留 ACL、扩展属性、硬链接关系或所有平台语义。对配置文件、可执行脚本等对象，应显式决定哪些元数据必须保留。

## 多文件修改怎样交付

可以先在隔离工作树应用全部 patch，运行验证后展示 diff，再由受控步骤接入用户工作区。若必须直接修改，应先检查所有前置条件，再按计划写入；失败后返回逐文件状态，不把部分成功简化成一个 false。

自动回滚也有条件：只有文件仍等于本工具刚写入的版本时才可回滚，否则可能覆盖用户后来编辑。备份不是无条件恢复许可证，回滚同样需要版本检查。

## 不要意外覆盖用户已有改动

任务开始记录 Git 状态或文件版本，但不要为了“清理环境”运行 destructive reset。修改前重新核对目标，结果报告说明哪些文件是本次新增改动，哪些原本就有未提交内容。提交工具应显式 stage 本任务路径，不能把工作区所有文件都加入提交。

## 验收矩阵

正常唯一替换、旧文本多处命中、重叠替换、读取后用户修改、两个路径指向同一文件、符号链接逃逸、编码错误、写满磁盘、rename 失败、修改后结果提交失败，都需要独立场景。最后一种会把控制流连接到第 17 章的未知结果恢复，而非简单再次应用 patch。
