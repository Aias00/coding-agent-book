第 2 章 如何读源码，以及贯穿全书的修复案例

从外部行为逆向追踪

读大型智能体仓库时，先统计目录数量很容易，判断真正的执行路径却更难。建议从可观察事件出发：界面显示工具开始、终端返回进程编号、恢复会话出现摘要，这些现象一定对应具体的协议数据和状态转换。找到它们的产生位置，再向上追踪谁调用，向下追踪谁提交结果，比从入口文件逐行展开更有效。

本书选择每个项目的核心循环、工具接口、执行管线、会话记录和压缩实现作为证据骨架。辅助文件用于解释局部机制，而非声称已经逐文件审计整个项目。附录的哈希表把研究对象固定下来：同名文件将来发生变化时，读者可以知道分析究竟对应哪一个版本。

一个有意简化的路径漏洞

贯穿全书的教学案例是：工作目录为 /work/demo，程序用字符串前缀判断路径是否在目录内。于是 /work/demo-backup/secret.txt 也可能被错误接受。预期修复是让程序根据路径层级判断归属，并补充边界测试。

输入：base=/work/demo，candidate=/work/demo-backup/a.txt
错误判断：candidate.startswith(base) 为真
预期判断：candidate 不属于 base 的子路径

这是教学用样例，不代表四个项目中存在同一漏洞。实验里的修复只演示词法路径关系；真实文件访问还要处理符号链接、大小写、挂载点和检查后替换文件的竞态。不能把一个 resolve() 或一个字符串辅助函数当作通用文件系统隔离方案。

任务如何转成可验证的执行链

我们希望智能体先读取函数与测试，再修改实现，执行定向测试，最后报告结果。每一步都需要留下证据：读到了哪个版本，改动前置条件是否满足，实际运行了哪条命令，退出状态是什么，测试的范围覆盖哪里。如果发生中断，还必须知道处于模型生成、工具等待、文件写入还是结果落盘阶段。

四套框架都可以承载这条工作链，但实现的责任分配不同。本书会反复追问：读取和测试能否并行？修改是否必须独占？用户说“只改测试，不要改实现”时如何进入下一次请求？测试返回十万行输出时怎样保留有效证据？用户在修改完成后、结果提交前终止进程时，恢复应该相信什么？

证据等级决定结论强度

固定提交上的函数体可以证明某条分支存在；它不能单独证明这条分支在所有产品入口都启用。一个配置字段可以证明系统能表达某种策略；它不能证明用户默认获得这项保护。测试可以证明列出的场景被覆盖；它不能证明未测试的权限组合安全。

Claude Code 的材料还多一层限制：package.json 声明版本 2.1.88，cli.js.map 包含源路径与嵌入文本。本书校验所引用的提取文件是否与嵌入文本一致，这能够排除这些文件在提取后被改写的情况，却不能证明发布包来源经过独立认证，也不能证明受构建条件控制的所有分支都进入了发行二进制。A01A02

阅读一段调度器时的提问顺序

先找输入：调用来自哪条消息，有没有唯一 callId，是否保留原始顺序。再找准备：参数验证、策略检查和工具查找分别发生在哪里。随后找执行：并发是否有上限，独占调用怎样形成屏障。最后找终结：错误如何表示，取消后是否补齐结果，日志提交与界面通知谁先谁后。

这样的读法能够避免一种常见误判：看到 Promise.all 就认为并发不受控制，看到 AbortSignal 就认为停止能够回滚副作用，看到 JSONL 就认为系统已经提供事务恢复。关键机制都在这些符号周围的状态条件里。

练习与检查要点

练习：为上述修复任务列出三个断电位置，并写出恢复策略。检查要点是：只生成了修改提议时可以重新请求；文件已经写入而日志缺失时必须检查现实文件，不能盲目重复；测试启动后失去进程信息时，必须先确定测试是否还在运行。恢复策略的差别来自外部世界的状态，而非“是否保存了聊天记录”。

后续实验会故意制造第二种情形，让你看到一个保守系统为什么宁愿报告结果待核验，也不声称已经完成“恰好一次”执行。
