第 12 章 执行隔离：文件、网络、身份与不可信仓库

DeepSeek：共享策略与执行后端分离

源码事实：SandboxExecutionPolicy 包含 mode、workspaceRoot 及可选 sessionId；mode 为 read-only、workspace-write、danger-full-access。接口明确声明它管理文件效果，网络和进程可见性不在这套词汇中。因此不能从 workspace-write 推断“禁止联网”，也不能从 read-only 推断“敏感文件均不可读”。D28

SandboxPolicyService.resolve() 的模式优先级为“本次显式模式 > 会话覆盖 > 部署默认”，工作区优先来自会话创建时的 cwd，缺少时才用配置的 fallback。显式模式是否已经获批由调用者在相应边界保证，resolver 本身不是审批器。会话覆盖由 sandbox/mode 日志事件恢复；当前事实另行提供给模型。路径保留执行世界的拼写，后端在真实文件系统上规范化。D29D14

sandbox-local 才负责实际约束命令。当前平台链如下，策略接口和后端选择不是同一件事：

平台 后端链 代码中需要注意的条件
Linux bwrap → Landlock 多候选时执行有时限的功能探测，Landlock 可报告 partial
macOS Seatbelt 默认单候选直接选择，执行时失败仍需处理，不能说启动前一定探测
Windows windows-acl restricted-token runner 当前实现明确报告 partial，不冒充绝对文件边界

SandboxEnforcement 区分 full 与 partial。这里的 full 也只针对该接口承诺的文件效果，不能扩大成网络、资源配额和全部系统安全已经完备。配置自定义 runner 会改变选择与探测语义；生产部署要验证该 runner 真正落实所声明的能力。D28D30

设计判断：返回“请求策略、实际后端、执行完整度、不可支持项”，比返回 sandboxed=true 更利于调用者决策。要求绝对边界的任务不应把 partial 当成 full；沙箱缺失和用户程序自身失败也应分别解释。

Codex：Linux 包装顺序与升级时保留禁止读取

LinuxSandboxCommand 明确描述默认 bubblewrap 文件系统隔离与 seccomp 系统调用过滤；use_legacy_landlock 是显式启用的旧路径。apply-seccomp-then-exec 分支解释了执行顺序：先让 bubblewrap 建立文件视图，再施加 seccomp 与 no_new_privs，避免过早收紧妨碍启动器建立隔离。不能把所有路径统一说成“只依赖 Landlock”。C22

权限升级还有一处重要保护：unsandboxed_execution_allowed() 检查文件策略是否含 denied-read。若有，直接退出沙箱会丢掉禁止读取的执行机制，所以不能将这类升级一概转成无沙箱运行；相关函数还调整升级参数以保留限制。编排器对特定远程执行器的能力也会进行核对。C12C05

原权限：工作区可写；敏感目录禁止读取
新需求：扩大某个写入范围
正确目标：扩大获准范围，同时保留禁止读取

上例是依据代码意图归纳的设计要求，不是对任意部署配置的实测证明。权限范围应能分别表达和合并，单个“普通/管理员”开关很难描述保留哪些限制。

Claude Code 与 Pi：接入点不等于全部隔离实现

Claude Code 的 sandbox-adapter 把设置转成 @anthropic-ai/sandbox-runtime 的配置，包括文件规则和网络配置；wrapWithSandbox 在沙箱启用时等待初始化，缺少初始化状态则报错，然后委托外部 runtime 包完成包装。仅凭 adapter 不能确认该依赖在所有平台的内部实现与实际隔离强度，也不能认为开关关闭时仍有同等限制。A18

Pi 本地 Bash 的默认路径直接通过 child_process 启动 shell，支持替换 BashOperations。project-trust 决定项目资源和扩展的信任，不在这两段代码中建立操作系统文件或网络隔离。其他组合可以增加执行后端；这里只能确认已阅读的默认本地路径，不能给整个生态作“完全没有沙箱”的结论。P17P09

设计判断：自建时可参考 DeepSeek 的策略/provider 分离和执行完整度，借鉴 Codex 在权限扩大时保持禁止项的处理；扩展后端时保留 Pi 的清晰 seam，并像 Claude adapter 一样明确初始化与依赖边界。上述组合是本书建议，不是任何一个项目现成的统一安全实现。

策略判断与真实限制分别负责什么

策略层决定某项行动是否被允许，沙箱负责限制程序真实访问资源。一个测试脚本可以绕开模型工具 API 直接打开文件或联网，因此只在 read_file 工具检查路径不够。进程内插件同样可能直接调用宿主 API，逻辑 scope 不会自动隔离恶意扩展。

本书建议执行器暴露 ExecutionProfile：

{filesystem_read_roots, filesystem_write_roots,
 network_policy, credential_refs, environment_profile,
 process_limits, executable_policy, lifetime}

这是控制面意图；provider 必须返回实际生效的限制及不可支持项。平台若无法落实某项强制限制，应拒绝启动或明确降级，不能仍把它显示为已隔离。

一次执行世界必须一致

读取、编辑、shell、LSP 与测试应作用于同一个 workspace 和 execution target。远程文件工具与本地 shell 混用，会导致模型修改 A 环境却在 B 环境测试。DeepSeek 的能力接口与共享 sandbox policy 解释了保持执行世界一致的重要性。D15D14

不要让控制面按自己的文件系统规范化远程路径。每个 provider 在实际执行世界解析和限制资源。workspace_id、显示路径与真实挂载路径分开保存，避免把容器内部路径当作宿主身份。

文件访问与挂载策略

为任务准备只读代码基础层与受控写层，可以减少误改范围；允许缓存、构建产物和依赖目录时，应单独声明。保护控制面数据库、授权材料和宿主元数据，不能因为它们位于工作区某个隐藏目录就暴露给测试进程。

符号链接与挂载逃逸应通过真实文件访问限制验证。容器内 root 不等于宿主 root，但容器配置、宿主挂载、设备、socket 和特权标志可能扩大权限。隔离强度取决于完整配置，不能只看采用了容器技术。

网络出站与凭据

网络策略至少说明允许目的地、协议、代理和 DNS 处理。只限制 URL 字符串而不处理解析与重定向，可能与实际连接不同。受控代理需要把拒绝原因关联到调用，而非让模型看到模糊超时后反复重试。

凭据通过短期、最小范围的引用注入执行层，尽量不进入模型文本。外部操作应有独立账号和业务审计身份。工具输出、失败栈、进程环境快照及产物下载链接都可能泄露凭据，需要在流出执行边界时检查。

资源限制也是隔离

限制 CPU、内存、进程数、磁盘、输出大小和运行时间，防止失控构建耗尽宿主资源。模型循环预算不能限制工具内部 fork 或日志洪水，因此必须由执行层落实。超额终止要留下哪种资源耗尽，以及哪些产物仍可信。

多租户环境还需要分别计算存储与网络成本。不能让一个任务用大量子代理或后台进程绕过父任务配额。

提示注入的防守位置

仓库文件、网页和工具输出是数据，不拥有改变用户授权的权力。上下文保存来源标签，策略不接受来自这些内容的“我已批准”。模型即使被说服提出上传请求，执行层仍按真实权限拒绝。

授权 UI 应引用原始用户目标与实际行动，避免把不可信文件中的解释直接当作批准理由。安全测试需检查真实网络和文件效果，不能只看模型是否口头拒绝。

分级实现路线

个人可信目录里的教学程序可以用严格路径检查和固定命令起步；执行不可信代码时，应增加真实沙箱；对外服务再加租户身份、隔离 worker、短期凭据和资源配额。升级时保持相同 Invocation 与 Outcome 协议，替换 executor provider。

本仓库参考实现没有操作系统沙箱，也没有暴露任意 shell。路径检查只用于可信单写者演示，不应通过修改几个配置就对外执行陌生仓库代码。

验收需要在真实目标平台尝试越界读写、派生子进程、访问禁用网络、重定向、资源耗尽与回收。配置文件写着 deny，不等于实际测试已经证明限制生效。
