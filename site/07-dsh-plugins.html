第 7 章 DeepSeek Harness：插件体系不是功能列表

从“全部是插件”追问到依赖结构

DeepSeek Harness 的核心组织原则是通过 Cordis 组合服务与能力。核心循环、会话、模型、工具、文件系统、子进程、沙箱乃至 UI，都有各自的插件位置。只说“它支持插件”远远不够：真正需要理解的是服务何时存在、消费者如何取得服务、注册怎样撤销，以及同一能力如何在不同 agent 范围内呈现。D01D16

一个提供 shell 功能的插件并不必然直接调用 Node 的 spawn。它可以依赖子进程服务；子进程服务又与文件系统、远程执行世界或沙箱协作。这样，把底层 provider 换为远程实现时，上层工具不必复制出一套“远程 Bash”。这种收益来自依赖结构，而非目录拆分数量。

能力接口的三种角色

架构文档把完整的能力接缝定义为服务声明、服务提供者和消费者三种角色。文件系统接口定义可调用的动作，某个本地或远程 provider 实现它，模型工具或语言服务使用它。一个只有接口定义、无人使用的包，还不能证明系统已经支持可替换执行。D15

修复案例中，读取、编辑、执行测试必须作用于同一个工作世界。如果文件工具读取远程文件，而 shell 仍在本机测试，就会产生“修改成功、测试却没覆盖修改”的假象。能力替换必须保持文件、进程和工作目录的一致性。抽象能否承载这种一致性，是比接口看起来是否简洁更有意义的判断。

注册是一种有生命周期的资源

工具注册、事件监听、UI 扩展都应有明确的撤销操作。Cordis 体系通过 effect 和 disposer 管理这些贡献。插件卸载后，旧工具若继续出现在模型请求里，就不仅是内存泄漏，也会造成声明与执行能力不一致。D05D16

一个常见错误是只在卸载时清空工具字典，却没有等待进行中的调用结束。另一种错误是在工具仍被使用时提前释放其连接池。生命周期管理需要先界定谁仍持有资源，再以明确顺序停止和清理；“支持热加载”因此并不等同于任意时刻替换实现都安全。

Scope 解决的是哪些隔离

scope 使用不透明对象身份标记注册范围，维护父子关系，并控制注册可见性和事件路由。子范围能够看到祖先层的注册，祖先监听者可以接收适当的后代事件。创建和释放范围也有独立的生命周期处理。D09

这让不同 agent 可以拥有不同工具与提示配置，而不必把所有策略塞进一个巨大的全局判断。它是逻辑范围隔离，不是操作系统沙箱。恶意同进程插件若本来就能调用宿主 API，scope 不会自动把它变成不可信代码容器。

配置与启动也是执行的一部分

该快照通过命名 dsh profile 启动受支持应用。profile 决定组合哪些服务和插件，补丁顺序影响最终配置。架构文档明确限制绕过统一启动器的应用入口，这有助于减少 SDK、桌面与 Web 各自启动一套不同运行时的漂移。D01

因此，分析某项能力是否启用时，应同时检查实现存在、provider 挂载、消费者挂载及 profile 组合。源码仓库有一个沙箱包，不能直接证明所有入口都使用该沙箱。

插件化的真实成本

插件结构使替换和扩展更容易，却把部分复杂度从函数调用搬到了依赖装配、事件顺序和销毁顺序。类型系统能约束服务接口，但运行时缺少 provider、事件被错误短路和卸载竞态仍需要显式处理。

设计建议是让配置错误尽早失败，并提供可查看的能力图。调试一个“工具为什么不见了”的问题，至少需要知道它在哪个 scope 注册、被哪个 profile 启用，以及哪个策略改变了可见性。
