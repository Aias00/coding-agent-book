第 3 章 Codex：回合执行与步骤快照

先找到真正的控制中心

本次快照中，Codex 的核心回合位于 codex-rs/core/src/session/turn.rs。run_turn 接受共享会话、回合上下文、输入、MCP 启动要求、可预热的模型客户端会话以及取消令牌。这组参数说明：回合执行不是一个只接收提示词的函数，它需要同时协调对话状态、执行配置和环境生命周期。C01

入口先处理前序异步 hook 的结果、模型客户端会话和采样前压缩。值得注意的是，压缩失败时不能把用户刚提交的输入丢掉。代码在相关失败路径保留输入后再发布错误，避免客户端已经对错误作出响应、执行器却还没完成输入记录的顺序问题。正常路径经上下文与工具准备后，才进入采样与工具的反复执行。

这个细节提示我们：输入被 UI 接收、被主循环接收、被写入可恢复历史，是三个不同的时刻。要向用户承诺“已收到”，就需要知道承诺对应哪一个时刻。

为什么同时需要 TurnContext 与 StepContext

用户回合可能包含多次模型请求。期间工具集合、模型信息或环境选择可能发生变化。Codex 为步骤保留 StepContext，工具运行时也明确保留公布该工具的步骤上下文。这样，即使工具异步运行，执行依据仍能对应到它被模型选择时的那份工具计划。C02C06

以修复案例为例：第一步模型看到搜索和读取工具；随后加载了一个额外扩展；第三步模型调用新工具。若所有调用都从一个不断变化的全局注册表读取配置，就可能出现“模型根据旧 schema 生成参数，执行器却套用了新实现”的错配。步骤快照降低了这种错配的可能性，也让日志解释更清楚。

这里的快照不是把操作系统冻结。文件仍可能被用户修改，远程服务仍可能改变。它固定的是运行框架用来解释这一模型步的配置与能力。因此写工具仍需要独立检查现实前置条件。

从响应事件到后续请求

采样消费路径处理结构化响应事件，包括输出项、文本增量和工具调用。工具 future 被收集并等待，执行结果进入后续上下文。needs_follow_up 则表达这一步之后是否还欠一次请求。不能把“出现助手文字”直接当成回合结束，因为同一次响应还可能带工具请求，后续也可能有待处理输入。C01

停止还要经过 stop hooks。hook 可以提出继续，并附带下一次请求所需的内容；没有可用内容的阻止请求会被特殊处理，而不是无条件制造空循环。代码也对某些内部会话来源使用不同的停止行为。这体现的是运行策略，不是语言模型天然理解“任务完成”。

中途输入不是简单追加字符串

输入队列保存用户输入、工具输出以及智能体间通信等不同类型，并维护活动回合的投递协调。用户在搜索结束后补一句“先别改实现”，这条输入需要在有定义的边界进入下一次请求。它无法取消已经发生的写入，也不应该被任意插入尚未完成的 JSON 工具参数。C13

工程上，输入队列至少要回答：何时认领一条输入，重试是否重复认领，取消后是否保留未消费输入，哪个回合拥有这条输入。仅仅使用一个线程安全队列不能回答这些语义问题。

回合边界带来的收益与成本

Codex 这种组织方式的收益，是把配置、工具计划、采样和停止策略放到可以追踪的生命周期内。代价是状态层次更多，扩展作者需要理解会话、回合和步骤的区别。阅读时应先找状态归属，再找功能名称，避免把全部上下文对象理解为同一个“全局 context”。

练习：模型已经生成编辑工具调用，用户的新消息也刚进入队列。你希望编辑立即停止，还是允许它完成后再处理输入？没有普遍正确的答案。检查要点是明确工具是否已开始、是否可以取消、取消后能否证明未修改，以及新输入进入下一次模型请求的时间点。
