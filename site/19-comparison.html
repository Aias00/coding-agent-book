第 19 章 横向比较：把名称还原为责任

先统一观察单位

比较四个系统时，最容易犯的错误是把不同层级的东西放在一起：用 Pi 的低层循环对比 Claude Code 整个产品，用 DeepSeek Harness 的插件目录对比 Codex 的一个工具。正确方式是先确定责任，再寻找每个项目承担相同责任的位置。

循环控制 Session 中的回合与采样 AgentLoop 的 turn/step agent-core 循环；应用再封装 query/queryLoop
工具组织 计划、路由、注册运行时 scoped 注册与能力服务 AgentTool 与执行钩子 Tool 定义与执行管线

同一个读取动作，四种组织路径

Codex 从当前步骤工具计划找到运行时，并通过公共执行机制处理；DeepSeek Harness 从 agent 范围内服务进入工具管线；Pi 从低层工具表与前后钩子进入工具实现；Claude Code 还把权限与呈现信息放进 Tool 产品协议。四者都可以“读取文件”，但扩展作者接触的接口与必须承担的责任不同。

迁移时不能只复制名称。一个读取工具从本地实现改为 SSH 实现，需要同步确认路径规则、编码、输出限制、取消和凭据；若测试仍在本机，整个修复链就失去一致性。抽象的价值应通过这样的替换实验判断。

三种顺序贯穿所有系统

模型源顺序决定助手提出 A、B、C 的顺序；执行完成顺序可能是 B、A、C；历史提交顺序则由框架选择。界面进度还可能形成第四种观察顺序。稳定系统会明确这些关系，而非假设它们总是相同。

并发不应由“越多越好”主导。对于网络读取，执行重叠通常有价值；对于共享文件写入，冲突可能使结果不可解释；对于昂贵模型调用，还需要预算和容量。最合适的策略取决于副作用、资源与观察要求。

架构取向与维护成本

显式编译期结构有利于发现接口不一致，但变更可能需要跨多个 crate；插件体系有利于运行时组合，但依赖与顺序错误更难仅靠类型发现；小内核容易理解，却要求应用补齐很多产品责任；集成产品使体验一致，却让工具接口和状态网络更复杂。

这些取舍没有绝对优劣。团队如果只需要内部单进程工具，完整插件平台可能引入过多维护；如果需要多个宿主、远程执行和第三方扩展，早期省掉的能力接口可能很快成为阻力。

可以组合的设计经验

一个新系统可以采用 Pi 式的清晰循环边界、DeepSeek Harness 式的可重建请求、Codex 式的步骤工具计划和审批编排，以及 Claude Code 式的人机呈现协议。组合的前提是定义统一事件与状态所有者，不能把四套对象模型机械拼在一起。

设计建议是先写一张责任表：每种状态由谁创建、谁修改、何时持久化、谁解释恢复。然后用同一项修复任务穿过系统，记录每个边界。真正的架构问题通常在交接处显现，而非单个模块内部。

阅读结果应如何表述

有源码依据时说“该快照的实现提供了这一机制”；只有接口时说“接口允许表达”；只有目录或特性分支时说“材料中存在相关路径”。没有统一实验时，不报告成功率、速度或成本排名。这样的精确表达并不削弱分析，反而使比较结论能够被读者复核。
