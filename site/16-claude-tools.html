第 16 章 Claude Code：工具接口如何同时服务模型与人

Tool 类型承担了完整产品协议

可见 Tool 定义不仅有输入 schema 和 call，还包括是否启用、是否只读、是否适合并发、中断行为、结果大小限制和呈现相关方法。某些字段取决于实际输入，而不是一个永远固定的工具标签。A04

这很合理：同一个 Bash 工具可以读取目录，也可以执行部署；同一个代理工具可以同步等待，也可以启动后台任务。产品需要根据这次输入解释风险、调度与显示，不能只从工具名称推导行为。

一次调用的可见路径

runToolUse 先在当前可用工具中查找名称，特定历史别名有受限兼容处理。未知工具返回可关联的错误结果。之后执行 schema 校验、工具自身输入校验、pre-tool hooks、权限决策、实际调用和结果处理。A06

这条路径把错误分成不同类别：工具不存在、类型错误、业务参数错误、权限拒绝与执行失败。模型可以对不同错误采取不同修复方式。若全部只返回“执行失败”，模型往往会盲目重试相同动作。

Hooks 改输入以后谁来负责

执行管线允许 hook 与权限流程影响处理后的输入。最终行动需要以实际决策后的参数执行，而不是审批 A、执行 B。可见实现专门保存和更新 processed input，并协调 hook 决策与常规权限路径。A06

对自建系统而言，这是需要重点测试的组合：参数改写后是否重新满足 schema，权限提示展示的是否正是将执行的内容，审计记录能否区分模型原始提议与最后实际执行参数。正文没有把这些问题全都归结为该产品已经完善解决，而是指出它们在实现中必须有责任归属。

流式工具调度如何减少等待

StreamingToolExecutor 在完整工具块进入后建立队列，根据工具定义和解析后的输入判断并发安全。并发安全的调用可以互相重叠，不安全的调用需要独占。结果按接收顺序缓冲输出，进度则有即时传播路径。A05

这不意味着只要 JSON 参数刚流出几个字符就执行。可用的完整块与未完成参数需要区分，否则会执行半截行动。流式调度节省的是“等待整个助手响应结束之后才开始所有工具”的额外间隙。

修复案例里，两个读取工具能尽早开始；编辑工具如果被判为独占，就不能与其他独占动作任意混跑。分类错误的后果依然由工具语义承担，调度器不会自动识别所有资源冲突。

同伴失败和用户取消不是同一种中断

执行器维护子取消控制器，对同伴 Bash 错误、用户中断及流式回退等情况产生不同的合成结果。工具还可以声明新用户输入到来时是取消还是阻塞等待，未声明有默认行为。A04A05

这样的差别直接影响体验。用户说“停一下”时，读取操作可以尽快取消；正在执行的关键写入可能需要先进入可解释终态。把所有工具统一暴力中断，既可能破坏数据，也会使恢复难以判断。

呈现接口为什么不是附属品

搜索、读取、编辑与权限拒绝在 UI 中需要不同解释。一个工具结果如果只携带长文本，界面就只能猜测这是 diff、错误还是后台任务状态。工具定义中的呈现与结构信息，让产品可以压缩重复读取、突出改动，并明确显示被用户拒绝的行动。A04

这种集成提高了体验一致性，但让通用工具接口更重。复用此类设计时，建议把模型内容、机器状态和呈现元数据分开定义，使无 UI 的调用者也能够理解结果，而不是依赖某个 React 组件才能知道执行是否成功。
