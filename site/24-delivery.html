第 24 章 交付路线：从可运行内核到可维护产品

第一阶段：单机闭环

交付任务对象、模型接口、工具注册、读取/编辑/验证、明确终态和事件存储。默认用脚本模型跑通，再接一个真实 provider。完成标准不是界面会显示 token，而是能够用证据证明修改基于正确版本、验证确实执行、预算与取消有效。

首版先限制工作区、命令和工具，不加入未经管理的动态扩展。工具数量少仍然通过完整授权与日志路径，为后续演进留下稳定基础。

第二阶段：可靠开发体验

加入真实进程管理、差异呈现、审批、工作区版本感知和上下文预算。产品先支持一种完整入口，再复用协议扩展 CLI、IDE 或 Web，避免每个入口自己实现一套循环。

交付检查包括：未保存 buffer、外部文件变化、长测试、取消、断线重连、审批过期和大输出。每项状态都能解释，不依赖开发者进数据库手工修复。

第三阶段：长期任务与远程执行

落实调用 replay policy、外部幂等、任务租约、fencing、产物存储和 worker 回收。跨进程后用认证的 Invocation 传递权限，服务端按 grant 与实际目标验证，不信任 worker 自报“已批准”。

存储迁移、备份与恢复要在上线前演练。长期任务一旦承诺可恢复，就需要明确哪些效果能自动重放、哪些只能核验，不能以“Beta”省略语义。

第四阶段：扩展与协作

先稳定 provider 接口和 disposer，再开放插件；先定义子任务产物与权限继承，再引入多 agent。每增加一个执行入口，都检查是否绕过授权、预算、取消或存储。多个产品入口应共享一套安全与状态语义。

不要用增加模型步数掩盖信息失真，也不要用更多 agent 掩盖检索不准确。按照失败分布决定投入位置。

一份实现完成度清单

模块 必须能回答的问题
循环 什么事实触发继续或停止，预算如何跨恢复保留？
模型 流是否完整，attempt 是否可见，协议转换是否丢信息？
工具 声明版本与执行一致吗，嵌套调用走同一管线吗？
修改 基于哪个文件版本，冲突时会不会覆盖用户工作？
权限 批准哪个参数、范围、身份和期限，变化后怎样失效？
隔离 实际限制落实在哪里，执行世界是否一致？
上下文 为什么选择这些内容，哪些证据已经过期？
恢复 派发后缺结果怎样处理，外部幂等由谁保证？
并发 谁是单写者，旧 worker 怎样被阻止？
产品 用户看见的状态是否对应确定事实？

清单不是额外审批流程，而是实现验收问题。答不出某一项，就应缩小公开承诺或补齐机制。

代码组织建议

agent/
  domain/       identity, messages, events, outcomes
  runtime/      actor, loop, inbox, budget, scheduler
  model/        preparation, protocol adapters, streaming
  tools/        registry, validation, policy pipeline
  execution/    workspace, processes, sandbox providers
  context/      selection, retrieval, compaction
  storage/      transactions, projections, artifacts, migrations
  integrations/ CLI, IDE, Web, MCP
  tests/        recorded streams, faults, task evaluations

目录只是起点。判断拆分是否有效，要看替换模型、执行器和存储时是否只触及相应边界。单个模块很长不是唯一坏信号；一个小功能必须修改所有模块，通常更值得关注。

如何使用四个参考项目

需要工具与步骤快照时查 Codex；需要服务替换与生命周期时查 DeepSeek Harness；需要小内核接口与持久任务模型时查 Pi；需要产品化工具呈现、审批与流式调度时查 Claude Code 可见材料。沿设计问题进入源码，而不是把某个项目的全部结构当作标准答案。

保留固定提交与实验。升级上游后复核接口、默认值、取消和持久格式；不能只更新依赖版本就沿用旧保证。静态分析、机制测试、真实模型任务评测和安全执行验证分别记录。

设计的最终标准

一套可维护的 Coding Agent，应能说明某项行动为何被提出、根据什么被允许、实际产生什么效果，以及下一步依据哪些已知事实。关键细节就在这些交接处：请求冻结、授权复核、派发提交、结果终结、版本失效与未知恢复。

模型让系统能够探索，确定性机制让探索能够被控制和验证。先把这些机制落实，再扩大工具、模型、宿主和协作范围，系统才有持续演进的基础。
