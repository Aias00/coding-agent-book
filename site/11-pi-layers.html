第 11 章 Pi：小循环内核与完整编程应用

不要把 Pi 当成一个单一包

Pi 仓库包含模型访问、agent 内核、编程应用、终端 UI 和其他应用包。本书重点区分四层：pi-ai 定义模型与消息协议；pi-agent-core 驱动循环；coding-agent 负责项目资源、工具和会话；实验性 durable 包另行提供持久任务机制。最后一项不能自动归到普通 coding-agent 的全部行为上。P01P04P12P15

这种分层让开发者可以只用循环内核，不必继承整套交互产品。但独立使用也意味着应用必须负责注入工具、保存历史、设定权限和组织恢复。代码少不意味着职责消失，而是某些职责交给了调用者。

AgentMessage 与模型消息的区别

应用内部需要保存通知、自定义消息和扩展数据，模型接口却只接受特定消息类型。Pi 的循环在模型调用边界先执行 transformContext，再执行 convertToLlm，最后归一化给 provider 使用的 transcript。P01P02

这是一条很有价值的边界：应用消息可以丰富，供应商协议可以变化，循环不必让所有内部类型直接暴露到每个 adapter。但转换函数必须清楚说明哪些内容被过滤、哪些变为用户输入，否则 UI 展示的历史可能与模型实际看见的历史不同。

相关接口还明确要求转换与流函数遵守失败表达约定。正常模型或运行错误应进入流的错误终态，而不是任意抛出异常破坏事件闭合。扩展作者如果违反这一约定，可能让上层缺少预期的结束事件。类型文档在这里规定的是运行语义，不只是参数说明。

循环为什么分两层

内层处理工具调用与 steering 消息；当自然工作将结束时，外层再检查 follow-up 消息。finishTurn 可以请求继续或结束，错误与中止响应则保留硬退出行为。这样，用户中途纠正与排在后面的独立任务能够有不同调度位置。P01P02

修复案例中，“改用另一个测试文件”属于当前工作的纠正；“修好后再写文档”可能属于后续任务。把二者都立即塞进下一次请求，会改变用户预期；把二者都等到任务结束，又会让纠正来得太晚。队列语义因此是产品行为，而非简单性能选项。

请求准备与下一轮准备

该快照的低层配置提供 prepareRequest 与 prepareNextTurn 等位置。前者紧邻每次对话请求，后者可以在后续轮次开始前更新上下文、模型或推理设置。压缩等较长准备期间，循环还需再次关注新到的 steering 消息。P01P02

这里有一个微妙约束：一次只取一条消息的队列模式，不应该因为准备前后各检查一次就注入两条。源码为这种情况安排了条件。这说明用户消息的认领数也是可观察语义，不能随意多取以“提高响应速度”。

工具变化进入 transcript

declareToolChanges 比较当前可执行工具与 transcript 已宣告状态，把新增和移除写入系统消息。这样工具集合不只是每次请求之外的临时参数，还能够作为对话状态的一部分解释。P01

这与 DeepSeek Harness 的请求头和日志约束有相似目标，但实现层次不同。不能因此认定两个项目共享同一会话格式，或可以直接重放彼此记录。对比应落在“声明变化可追踪”这一机制，而非仅看都有 system message。

适合复用哪一层

如果你需要自定义运行方式和界面，可以从模型层与 agent-core 开始；若你需要现成的文件工具、资源加载和会话浏览，应研究 coding-agent；如果要进程崩溃后继续任务，应单独评估 durable 的版本与承诺。先选择职责，再选择包名，能避免为一个轻量原型意外引入完整产品复杂度。
