第 24 章 从研究到自建：一条可维护的实现路线

先选择责任范围

如果目标是一个仅供内部使用的编程助手，可以先选择现有运行框架并限制工具；如果目标是服务多个宿主和执行环境的平台，需要更早设计能力接口；如果目标是嵌入已有产品，结构化协议和人机交互可能比终端 UI 更重要。选择架构之前，先明确自己愿意长期维护哪些责任。

下表是依据本书快照的工程适配建议，不是购买建议或实时产品排名。

主要需求 优先研究的材料 必须额外核对
嵌入结构化编程执行能力 Codex app-server 与核心协议 协议版本、部署环境、身份与审批集成
可替换服务和多种运行宿主 DeepSeek Harness 能力接口 profile 组合、插件生命周期、版本稳定性
自定义循环与工具，控制应用复杂度 Pi agent-core 与 coding-agent 存储、授权、取消和所选层级
跨进程恢复的任务模型 Pi Durable 实验性 API、重放政策、外部幂等
研究产品化工具和权限体验 Claude Code 可见发布包 材料范围、构建门控、版权与服务可见性

第一阶段：完成最小闭环

实现一个模型 adapter、一种消息历史、读取与编辑工具、一个测试执行器和明确的停止条件。所有工具都返回结构化成功或失败。先用确定性假模型验证正常执行，确保任务能从读取走到验证。

这时不要急于增加插件市场、多 agent 团队或长期记忆。若主循环连模型错误与工具错误都分不清，功能越多只会使恢复更难解释。

第二阶段：建立执行边界

加入 schema 校验、工作区限制、工具前置条件与权限范围。分开项目资源可信度和每次行动授权。对于 shell，明确继承哪些环境变量、是否联网、如何停止进程树，以及后台进程由谁回收。

同时让 UI 区分等待模型、等待工具、等待用户和结果未知。状态准确比动画流畅更重要，因为用户需要根据状态决定是否继续编辑同一文件、关闭会话或等待测试。

第三阶段：把记录做成事实接口

为输入、模型尝试、工具调用和结果分配身份，规定提交顺序。保存能够重建模型实际请求的内容或受控引用。压缩应留下边界与恢复元数据；扩展不能在未记录的暗处改变模型可见输入。

这一阶段还应建立数据保留政策：哪些内容是会话事实，哪些只是临时进度，哪些原始输出需要过期。日志越多并不自动越好，尤其当它包含用户代码和凭据时。

第四阶段：用故障决定持久化方案

先注入中断，再设计恢复。确认工具哪些可以安全重跑，哪些必须核对，哪些需要用户决策。若需求仅是重开会话浏览历史，不必声称拥有持久任务引擎；若需求是跨天执行并继续等待，就需要检查点、任务归属和可持久计时器等机制。

测试磁盘写入失败、损坏尾部、旧版本格式、部分工具成功和队列待处理输入。把不能自行恢复的状态暴露出来，而不是用无限自动重试隐藏它。

第五阶段：优化关键路径

有数据后再做请求预热、并行读取、延迟工具发现与输出裁剪。每次优化都验证任务质量与可解释性。例如更激进截断节省 token，却可能增加重复读取；增加并发缩短单项等待，却可能放大服务限流和共享状态冲突。

多 agent 应用于可明确分工、能独立验证的子任务。共享文件写入需要归属或隔离，父代理还要验证整合结果。让更多模型同时工作不等于降低总成本，也不自动提高正确率。

出版工程也是一项可验证任务

本书的交付本身采用同样原则：章节是源数据，构建脚本形成 EPUB 与在线页，校验脚本检查导航和资源，GitHub 工作流发布同一份产物。源码分析证据、实验结果和出版验证分别保存，避免把一次生成成功误写成全部内容已经运行证明。

维护本书时，应先固定新的源码提交，再复核受影响章节和引用；不能只更新日期。若某个文件移动，更新证据索引之前要确认机制是否也变化。给分析书籍保留版本，比不断把旧结论装进新封面更有价值。

最后的工程判断

可靠的编程智能体需要同时回答三件事：它为什么提出这项行动，它实际上做了什么，下一次执行应该基于哪些已知事实。模型能力决定提议的质量，运行框架则决定这些提议怎样成为可控制、可观察、可恢复的工程过程。

继续阅读上游时，带着这三个问题追踪一次真实任务。找到具体状态、事件和执行边界之后，复杂仓库就不再只是庞大的目录，而成为一组能够复核的设计选择。
