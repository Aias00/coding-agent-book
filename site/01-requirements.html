第 1 章 需求建模：Agent 到底要交付什么

将自然语言目标变为验收条件

“修复路径校验漏洞”不是完整工程需求。我们把教学任务限定为：修复 /work/demo-backup 被误认为 /work/demo 子目录的问题；接受正常子路径和工作目录本身；拒绝词法上的父目录逃逸；补充测试；只修改指定实现和测试文件；报告实际检查。符号链接隔离属于执行环境设计，不能靠这个词法函数承担。

一个任务对象至少包含：

TaskSpec {
  objective, acceptance_criteria[], workspace_id,
  allowed_changes[], forbidden_actions[],
  verification_plan[], budget, completion_policy
}

objective 供模型理解，allowed_changes 和 forbidden_actions 还要传给工具授权层。verification_plan 指定可运行检查；completion_policy 定义没有完成检查时应返回“部分完成”还是继续尝试。不能把所有字段拼成一段提示词之后，就丢弃机器可检查的信息。

完成状态应该至少有五种

状态 具体含义 必须提供的证据
completed 修改和必要验证均完成 变更摘要、测试结果与范围
partial 有可交付修改，但部分检查未完成 已完成项、剩余项与原因
blocked 缺少权限、环境或必要输入 阻塞点、恢复条件
cancelled 用户要求停止，运行已收敛 已发生动作与仍待核验状态
failed 当前预算与恢复策略下无法推进 错误类别和保留产物

此外，单次工具可能是 unknown，表示派发后结果不明。任务终态与工具终态不能用同一个枚举：一个测试结果未知的任务，可能以 partial 结束，同时保留待核验调用。

Agent、脚本与工作流如何分工

模型适合在不完整信息下选择读取位置、解释失败并提出修改。确定性程序适合检查参数、路径、预算、版本和调用身份。固定的发布步骤适合显式工作流。把需要强制执行的规则留给模型记住，会使正确性依赖每一次生成；把所有判断写成规则，又会失去处理新问题的能力。

参考方案让模型选择下一步行动，由执行器验证行动能否执行；验证器判断可检查的验收条件；停止策略合并模型意图、预算与验证状态。最终回答是一份报告，不是唯一完成证据。

建立能力与风险矩阵

先列出搜索、读取、编辑、测试、联网、依赖安装、Git 提交和发布。逐项写清输入、输出、真实副作用、所需权限、可否重试、可否取消和验证方式。例如读取可能安全重试但不能无限读取；测试脚本可能写缓存、联网或启动进程，不能因为名称是 test 就自动归类为只读。

第一版可以只提供工作区搜索、限量读取、精确编辑和固定验证命令。安装依赖、任意 shell 与外部发布需要更完整的权限和执行环境。能力少的起点仍应经过与未来工具相同的调度、日志和授权路径，避免第二版再重写内核。

把性能要求写成可测试约束

不要只写“响应快”。可以规定：工具进度每秒最多发布若干次；单次读取限额；最大模型步数；并发工具上限；取消后多长时间进入收敛状态；超过日志保留量如何归档。具体数值是可配置的部署参数，不能散落在业务代码里。

预算至少包括模型请求次数、输入输出 token 估计、工具运行时间和总墙钟时间。不同预算分别触发不同结果：模型调用额度耗尽可以保留已完成修改；命令超时需要停止进程并判断结果；用户取消应优先于继续探索。

本章产物与验收

产物是一份 TaskSpec、能力矩阵和终态表。验收时先不给模型，直接向执行器提交超出范围的编辑、超额读取和未经授权命令，确认它们被拒绝。如果系统只能通过提示词阻止这些动作，需求尚未落到实现中。
