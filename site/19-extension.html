第 19 章 扩展机制：依赖注入、生命周期与协议版本

Tool、Skill 与 MCP 的分工

本节先依据源码区分三类对象，再解释它们怎样协作。Tool 是可执行接口；Skill 是任务方法及配套资源；MCP 是把外部服务能力接入宿主的协议。它们可以组合，但不需要把一个 Skill 直接注册成同名可执行函数，也不能认为连接 MCP 就等于把服务全部内容直接发送给模型。

对象 宿主管理什么 模型通常接触什么
Tool 定义、运行时、版本、执行上下文与策略 名称、说明、参数 schema，以及调用结果
Skill 名称、适用说明、正文、脚本、引用资源、来源与可见性 先接触目录，激活后读取具体指令
MCP server 配置、连接、认证、能力同步、调用与清理 经宿主转换和筛选后的工具或资源入口

上表是跨项目的职责归纳。各项目的真实暴露位置与加载机制，以下分别注明。

Pi 的 Skill：目录进入提示，正文通过读取加载

源码事实：loadSkills() 和目录扫描逻辑查找 SKILL.md，解析名称、description 与调用控制。formatSkillsForPrompt() 先过滤 disableModelInvocation，再生成 <available_skills>，其中包含 name、description 和 location。目录向模型说明何时读取 Skill 文件，相关相对资源按 Skill 所在目录解析。P19

发现 Skill → 解析元数据 → 过滤模型可调用项
→ 将名称、简介、位置放入提示
→ 模型按需通过 read、bash 或间接入口加载正文
→ 依据正文调用真实工具

这里是渐进加载：目录让模型知道有哪些方法，正文提供具体操作。Pi 这段函数还根据可用读取入口改变指引文字；不能把它描述成所有情况下都存在一个 load_skill 函数。模型禁用项可以有显式用户入口，具体指令形式由该宿主定义，不能把不同项目的斜杠命令混为统一协议。P19

设计判断：这种方式容易接入已有文件工具，减少新接口；但宿主必须保证正文位置可访问、来源可信，并使活跃指令在压缩后仍可恢复。只列简介而没有可用加载入口，不能形成完整 Skill 能力。

DeepSeek Harness 的 Skill：注册表、目录和 loader 分开

源码事实：SkillRegistry 合并 provider 与运行时贡献，按 scope 和来源规则提供 list、snapshot、get。读取来源由 provider 决定，注册表本身不等于文件扫描器。tool-skill 再把目录与加载入口提供给模型。D24D23

模型激活路径通过 skill 工具加载正文，使用 renderSkillContent() 返回一致指令形式，结果进入普通工具历史。用户显式激活则从已认领的用户消息中识别 /name，检查 user-invocable，再把相同渲染形式作为指令上下文加入 step。未知或用户禁用名称留作普通文本，不自动执行。D23

这份目录不是固定在 system prompt 的静态字符串：agent/pre-step 检查当前 agent 是否真能看见该插件注册的那个 skill 工具，再取得完整 snapshot、过滤 model-invocable 项、计算目录摘要，与已发布目录比较。目录变化时发布替换目录；曾发布后变为空，也会发布空目录，明确退休旧名称。provider snapshot 不完整则保留上次可靠视图，不用临时缺失抹掉目录。D23

一个细节很重要：工具可见性比较的是定义身份，而不仅是名字。另一个 scope 注册同名 skill 工具时，不应自动继承原插件的目录和加载语义。目录消息的角色、来源与记录方式都由实现确定；不能把 Skill 目录一概说成 system 指令。D23

设计判断：把 provider、registry、目录呈现和正文 loader 分开，有利于本地、远程和按 agent 配置组合，但增加了目录一致性与生命周期成本。Skill 里的脚本仍需要执行工具，Skill 提到某个 MCP 能力也不自动为它授权。

扩展点按责任定义

常见扩展包括模型 provider、工具、上下文贡献、执行器、存储 provider 和 UI renderer。不要用一个任意修改全局对象的 callback 承载所有功能。每类扩展声明输入、输出、顺序、是否可短路、错误归属与资源释放方式。

Extension {
  id, version, required_services[], provided_services[],
  register(context) -> Disposable,
  compatibility, trust_requirement
}

服务定义接口，provider 提供实现，consumer 使用接口。DeepSeek 的能力接口明确采用这三类角色；Pi 的扩展类型与 runner 则展示钩子式组织。D15P10P11

装载时先检查依赖图

构造有向图，检查缺失服务、重复 provider、循环依赖与版本不兼容。只有配置完整才激活消费者。不要发现 provider 缺失就静默跳过工具，否则用户看到的是能力随机消失。

加载失败需要回滚已注册贡献。注册返回 disposer，组合器按逆序撤销；已经启动的连接和 worker 也要等待清理。将“注册是一种资源”写进 API，能避免插件卸载后残留工具和监听器。

Scope 是可见性范围

不同 agent 可以拥有不同工具与上下文贡献。scope 决定注册继承和事件接收，不能用字符串 prefix 代替真实身份。DeepSeek 使用不透明 scope key 与父子链，提供了避免范围混淆的参考。D09

scope 不阻止同进程恶意代码访问宿主模块。第三方不可信扩展应通过独立进程或受限协议运行，只得到明确定义的能力。安装一个具有宿主代码执行权的插件，本质上是重要信任动作。

热卸载要先停止新的借用

推荐状态 active → draining → disposed。draining 后不再把工具放入新 ToolPlan；已有步骤持有旧 runtime 引用，完成或取消后释放。引用数归零再关闭连接与卸载代码。超时无法清理时，报告 leaked/failed 状态，而不是假装释放成功。

同名新版本不能直接替换旧调用。旧调用恢复需要原版本或明确迁移策略；缺少原实现时返回阻塞，而不是用新参数解释猜测。

钩子组合需要定义短路规则

观察型钩子只读取事件，策略型钩子返回决定，中间件型钩子通过 next 继续。不同类型不要混成一个模糊返回值。瀑布中不调用 next 会短路，因此注册顺序属于行为语义。D16

mandatory guard 不接受普通插件放宽，后置脱敏不改变真实执行效果。插件异常由框架归一化，并说明是在准备、执行还是呈现阶段失败。一个日志插件报错不应无条件回滚已经完成的写操作。

MCP 接入的实际工作

源码事实：DeepSeek 的 mcp-client.apply() 先校验连接配置和服务命名空间，建立 connection supervisor，再等待初始连接与工具发现。supervisor 管理连接代际、重连、活动工具注册与卸载清理。failOnStartupError 会影响初始失败处理，因此“配置存在”“服务已连上”“工具已注册”是不同状态。D25D26

syncTools() 将服务端工具转换为普通 ToolDefinition：description 和 inputSchema 进入宿主定义，execute 路径最终使用 client.callTool。模型调用仍经过普通 ToolRuntime，而不是绕过宿主直接控制服务器。D27

client.listTools()
→ 构建下一代 ToolDefinition
→ ctx.tools.register(definition)
→ 本轮工具计划筛选与暴露
→ 模型提出调用
→ 宿主校验、策略与调度
→ client.callTool({name: rawName, arguments: args})
→ 结果归一化并进入历史

这是一条依据实现整理的时序，省略协议协商、网络认证等传输字段，不能直接当作完整 MCP wire request。MCP 还可以提供资源，宿主是否暴露读取入口、怎样将内容纳入上下文，是另一层适配；DeepSeek 的这份桥接文档明确说明其能力和不支持项，不能把协议所有特性都归给一个插件。D26

公开名称与原始名称不能混淆

publicToolName() 根据本地配置的 serverName 与 rawName 形成模型名称，常见形式为 mcp__github__get_issue。该实现还处理目标模型的字符与 64 字符限制；发生有损规范化或截断时附加身份摘要，降低名称碰撞风险，重复定义仍由同步逻辑检查。这个公开命名策略属于宿主，不是 MCP 强制格式。D27

真正调用远端时，代码保存并使用原始 tool.name。它不从公开名称按下划线反向拆出 rawName，这避免名称规范化后错误路由。

工具同步失败的两个阶段

syncTools() 先获取完整列表并构建下一代，再切换注册。发现失败或列表重复发生在第一阶段，旧代保持不动；进入第二阶段后先撤销旧代，再注册新代。若新注册与其他贡献冲突，会撤销已注册的部分，最终该服务不留下半套工具，可能变为零项或抛出错误，取决于调用配置。不能笼统声称所有同步失败都保留旧代。D27

源码还分别处理取消信号、调用超时和 MCP 错误结果；模型收到失败，不伪装成功。结果中的文本、结构化值和图片等需要适配与策略处理，不能仅把返回对象随意转成字符串。要求 task-based execution 的工具在此桥接不支持时会明确拒绝。D27

设计判断：统一 ToolRuntime 能复用校验与策略，明确命名空间有利于权限和审计。远端声明不应自动成为强授权依据；重连后 schema 或目标变化，需要让后续工具计划和授权同步更新。这个约束属于自建系统的设计要求，不能仅凭成功 listTools 就认为已经满足。

三者协作：处理一个 GitHub Issue

下面是基于前述能力的组合示例，不代表某个项目存在同名内置 Skill：用户要求修复一个 Issue；模型从目录选择适用 Skill，加载调查与验证方法；经 MCP 工具读取 Issue；经本地文件工具调查、编辑；经验证工具取得结果；最后按 Skill 的要求报告。

Skill 决定方法，Tool 提供行动接口，MCP 把一部分行动接到外部服务。所有真实行动仍由运行时接纳和执行。完整定义、当前会话允许项、本轮可见项、已加载 Skill 内容与外部连接状态应分别管理；压缩后怎样恢复它们，见第 15 章的 Claude Code 路径。

Code mode 不应该绕过底层工具

让模型写一段程序批量调用工具，能减少请求往返，但带来脚本 CPU、内存、运行时间和嵌套调用管理。脚本只拿到受控工具代理，不拿宿主任意 API；每个嵌套调用走共同策略与记录路径。

如果脚本中断，已完成子调用结果应可发现；重跑脚本需要稳定 nested key 和子调用 replay policy。Pi Durable 的嵌套调用和 Pi 通用 runToolCall 分别提供持久与非持久层面的参考。P12P01

验收

缺少 provider 要在启动时失败；加载一半异常要撤销注册；卸载期间新请求看不到工具、旧调用仍正确结算；renderer 故障不丢执行结果；远程 server 改 schema 不用旧 grant；嵌套调用不能绕过权限。插件市场和动态安装应在这些机制稳定后再开放。
